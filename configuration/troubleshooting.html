配置故障排查：按症状找到失败位置 ​

排查配置问题时，先确认失败发生在哪一层：进程创建、启动生命周期、外部依赖、请求安全、仓库授权，还是运行时覆盖。不要只看 /health 的一个 ok。

API 在输出监听地址前就退出 ​

症状 ​

错误提到 SECRET_KEY、ENCRYPTION_KEY、MCP_KEY_PEPPER、安全 Cookie、OPAQUE_SERVER_SETUP 或开发本地路径开关。

检查顺序 ​

  1. 确认前三个密钥都至少 32 个字符、互不相同，并且不是 change-me 或 replace-me。
  2. 若环境是 prod 或 production，确认 SESSION_COOKIE_SECURE=true。
  3. 确认 SESSION_COOKIE_SAMESITE 是 lax、strict 或 none。
  4. 生产环境必须设置稳定的 OPAQUE_SERVER_SETUP，并关闭 ALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHS。

修复成功的标志 ​

应用能完成创建并进入启动生命周期，不再出现同一项校验错误。此时仍需继续检查数据库连接，因为设置校验通过不代表生命周期启动完成。

API 创建成功，但启动生命周期失败 ​

症状 ​

服务在连接数据库、读取系统设置或初始化登录材料时退出，没有进入稳定监听状态。

检查顺序 ​

  1. 核对 DATABASE_URL 的驱动、主机、端口、数据库名和凭据。
  2. 确认数据库已运行，并且当前账号可以读取、写入和执行升级后的表结构。
  3. 在已有依赖的环境执行 uv run ershu-db heads，当前源码应显示迁移 head 为 0002。
  4. 需要升级时执行 uv run ershu-db upgrade head，然后重新启动 API。

当前有一项已知源码冲突：core/tests/test_migrations_postgres.py 的 PostgreSQL 集成断言仍期待 0001，而实际最新迁移是 0002。排查数据库版本时应以迁移目录和 ershu-db heads 为准，不能把这条旧断言当成当前期望。

修复成功的标志 ​

API 保持运行，GET /health 返回 {"status":"ok"}，且不再在生命周期初始化阶段退出。

/health 正常，但依赖检查是 degraded ​

GET /health 和 GET /api/v1/health 只返回进程存活状态。GET /api/v1/health/dependencies 才会检查数据库和 Milvus，而且即使降级也仍返回 HTTP 200。

返回字段说明下一步
database.ok: falseselect 1 失败检查 DATABASE_URL、网络、凭据和数据库状态
milvus.ok: falseMilvus 连接或查询失败检查 URI、令牌、数据库名和服务状态
status: degraded上述至少一项失败修复对应依赖后重新请求，直到两项都为 true

该端点不检查 Redis、Worker 或模型通道，不能作为整套系统就绪证明。

登录返回 503，但依赖检查正常 ​

登录限流在首次使用时连接 REDIS_URL。地址为空、客户端未安装、连接失败或 Redis 返回无效计数时，API 会把错误映射为 503。

检查 Redis 地址和网络后，再完成一次真实登录请求。成功标志不是依赖检查变化，而是登录流程不再因为限流存储不可用而返回 503。连续失败达到当前的 5 分钟内 8 次限制后，仍会被正常限流。

生产 API 返回“需要 HTTPS” ​

生产环境下，API 会拒绝方案不是 HTTPS 的 /api/ 与 /mcp 请求。若浏览器实际使用 HTTPS，但后端仍看到 HTTP：

  1. 确认反向代理把原始方案正确写入转发头；
  2. 确认 PROXY_HEADERS=true；
  3. 把实际代理地址加入 FORWARDED_ALLOW_IPS，不要信任无关来源。

修复后，同一 HTTPS 请求应进入正常路由；直接 HTTP 请求仍应被拒绝。

浏览器写请求返回 403 ​

先看错误内容：

  • Cross-site request blocked：请求的 Origin 或 Referer 不等于当前站点，也不在 CORS_ORIGINS；
  • csrf_invalid：X-Ershu-CSRF 请求头缺失，或与 CSRF Cookie 不一致、签名无效。

读取请求不会触发这项写请求检查。Cookie 登录的写请求必须通过 CSRF 校验；浏览器带有 Origin 或 Referer 时，来源也必须允许。Bearer 请求不使用 Cookie 身份，因此不需要 CSRF，但仍要提供有效令牌。

修复成功时，来自允许来源、带匹配 CSRF 头与 Cookie 的写请求进入业务路由；故意移除 CSRF 头时仍返回 403。

远程仓库地址被拒绝 ​

错误通常能直接指出类别：

错误方向检查项
协议不允许默认只用 HTTPS、SSH 或 SCP 风格地址；不要为了省事打开不安全协议
主机不允许非空 GIT_ALLOWED_HOSTS 必须匹配精确主机或通配规则
主机无法解析检查 DNS 和主机拼写
解析到受阻地址默认拒绝私有、回环、链路本地等地址；私有 Git 服务需要精确加入允许列表，回环仍不会放行

运行时修改主机列表后，重新读取管理员设置，确认目标项的 source 和 value；再发起一次新的克隆或拉取。已有失败操作不会自动重放。

本地仓库路径不受信任 ​

合法路径应当位于受管缓存中、进入 TRUSTED_LOCAL_PATHS，或自身包含 .git。相对路径会按服务进程的当前工作目录解析，因此部署时更适合使用清楚的绝对路径。

开发开关 ALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHS 只在非生产、没有受信任列表时兜底。生产环境不能使用它。修复成功时，新建工作区不再报告 Repository local_path is not trusted，而不需要放宽整个文件系统。

管理员修改设置后没有生效 ​

按下面顺序区分原因：

  1. 从 GET /api/v1/admin/system-settings 找到目标项。
  2. 若列表中没有该项，它不是可在线覆盖设置；修改环境变量后重启对应进程。
  3. 若 source 是 environment，数据库覆盖并不存在；检查更新请求是否成功。
  4. 若 source 是 database，确认 value 是目标值，并记住它通常只影响后续操作。
  5. API 实例会在启动和每 30 秒刷新；Worker 使用自己的刷新点，不能用 API 周期推断 Worker 状态。

未知名称、类型错误和越界值由管理服务拒绝。不要直接向数据库写 JSON 来绕过校验；无效行会让周期刷新持续报错。

开发文档页面消失 ​

/docs 和 /redoc 只在 ENVIRONMENT 精确等于小写 development 时启用。Development、dev 或生产值都不会打开它们。修改后重启 API，因为环境设置已经缓存。

依赖安装无法从公开源完成 ​

当前 API 的 pyproject.toml 把 Core 固定到一个私有 Gitea 提交。没有该源的读取权限时，依赖解析失败是当前发布条件的限制，不是换一个公开包地址就能修复的问题。

请使用已经准备好的内部工作区或等待公开发布流程完成。不要擅自改远端地址、伪造公共依赖，也不要把私有凭据写入配置示例。

源码位置 ​

  • core/src/ershu/core/config.py：设置与安全校验错误。
  • core/src/ershu/db/migrations.py、core/alembic/versions/：迁移入口和当前版本。
  • core/tests/test_migrations_postgres.py：仍断言旧版本的已知测试冲突。
  • api/src/ershu/api_main.py：创建、启动、HTTPS、来源和 CSRF 处理。
  • api/src/ershu/api/routes/health.py、api/src/ershu/api/database.py：存活与依赖检查。
  • api/src/ershu/api/services/auth/login_limits.py：Redis 连接和 5 分钟内 8 次失败限制。
  • core/src/ershu/services/repositories/git_url_security.py：远程主机拒绝原因。
  • core/src/ershu/tools/readonly_repository/workspace.py：本地路径信任规则。
  • api/src/ershu/api/services/system_settings.py：运行时设置来源、校验和重置。
  • api/pyproject.toml：当前私有 Core 固定来源。
