先按能力理解配置 ​

Ershu 的配置分散在 Core、API、Worker、MCP 和前端五个模块。先从要启用的能力出发，再进入具体参数，通常比逐个填写环境变量更容易发现缺项。

先认清三类设置 ​

类别典型内容何时读取修改方式
启动必需项数据库地址、加密密钥、监听地址进程启动时环境变量或环境文件；通常需要重启
可在线管理项Worker 并发、预算、检索限制、依赖来源服务运行期间管理界面或管理 API；数据库值可覆盖启动值
前端构建项API 基础地址、开发代理地址构建或启动前端时VITE_ 环境变量；改动后重新构建

Core 是共享包，不是独立进程。API、Worker 和 MCP 都会读取 Core 的数据库、安全与检索设置；同名设置不代表每个进程会自动共享环境，部署时仍要保证需要它的进程拿到一致值。

分析能力需要什么？ ​

API 负责验证请求并创建运行记录，Core 把任务和状态写入 PostgreSQL，Worker 再领取任务。Redis 用于短期缓存和分布式协调，但它不代替持久任务队列。仅启动 API 不会执行分析。

生成项目文档依赖模型通道。模型通道不是环境文件中的单个通用密钥，而是由管理员通过网页或 API 创建、测试并启用的记录。Worker 领取任务时读取选定通道，并按任务预算调用模型。

首次运行必须覆盖项目中的所有有效仓库。完成基线后，才可以针对变更提交创建增量任务。这个限制由 API 校验，不应通过直接改数据库绕过。

检索能力需要什么？ ​

词法搜索读取已经生成的代码索引。语义搜索还需要 Milvus 和有效的嵌入设置；混合搜索会组合两类结果。

请把“服务能启动”和“检索已就绪”分开验证：

  1. 确认 Milvus 可以连接；
  2. 确认嵌入模型设置有效；
  3. 确认目标项目已经完成包含搜索索引的分析；
  4. 发起一次带明确模式的查询，检查响应中报告的实际模式和回退原因。

语义模式出错时不会静默返回词法结果。混合模式在特定失败下可以明确回退，因此调用方应读取响应状态，而不是只看是否有结果。

访问与自动化需要什么？ ​

网页登录使用 OPAQUE 密码流程和会话 Cookie。会改变状态的浏览器请求还受 CSRF 与来源检查保护。MCP 使用 Bearer 凭据，密钥带项目范围；两套入口不要共用凭据。

远程仓库凭据经过应用层加密后保存。加密密钥、会话密钥、MCP 密钥哈希密钥和 Webhook 签名密钥都应使用彼此独立的随机值。轮换前先阅读权限与安全，因为部分密钥变化会使已有数据或会话失效。

定时轮询由单独的 ershu-api-poller 进程执行。Webhook 则由 API 验证时间戳、随机数和原始请求体的签名。两种方式都只负责创建任务，后续仍依赖 Worker。

下一步怎样读？ ​

  1. 用基础配置建立可以启动的最小环境；
  2. 用加载与覆盖规则确认哪个值真正生效；
  3. 按模块配置准备每个进程；
  4. 在环境变量参考查类型、默认值和限制；
  5. 上线前完成权限与安全清单；
  6. 失败时按配置故障排查定位。

事实来源：五个模块的设置类型、运行时设置服务、任务队列与分析测试、搜索响应契约、认证和 Webhook 安全测试。
