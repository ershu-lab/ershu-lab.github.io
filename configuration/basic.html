基础配置：先让服务安全地启动 ​

本页解决一个问题：在已有 Ershu 开发工作区或已经安装好各模块的环境中，API 至少需要哪些配置才能安全启动。

当前后端仍固定引用私有 Git 源中的 Core 版本。因此，本页不代表可以仅靠公开软件包完成全新安装，也不会提供无法公开验证的安装承诺。

先准备三个外部服务 ​

服务API 怎样使用配置入口
PostgreSQL保存账号、项目、任务、文档和系统设置；API 启动时会读取数据库DATABASE_URL
Redis保存登录失败计数，用于登录限流REDIS_URL
Milvus保存和查询向量索引；依赖检查会主动连接它MILVUS_URI、MILVUS_TOKEN、MILVUS_DB_NAME

API 启动依赖数据库。Redis 连接在首次使用登录限流时建立，Milvus 则由检索流程和依赖检查使用。只看到进程启动，并不能证明这三个服务都可用。

写一份最小开发配置 ​

API 和 Core 都通过 Pydantic Settings 读取进程环境变量和名为 .env 的文件。下面的片段适合本机开发，尖括号中的内容必须替换，不能原样使用。

dotenv
ENVIRONMENT=development
LOG_LEVEL=INFO

DATABASE_URL=postgresql+asyncpg://ershu:<database-password>@localhost:5432/ershu
REDIS_URL=redis://localhost:6379/0
MILVUS_URI=http://localhost:19530
MILVUS_TOKEN=
MILVUS_DB_NAME=default

SECRET_KEY=<independent-random-value-at-least-32-characters>
ENCRYPTION_KEY=<different-random-value-at-least-32-characters>
MCP_KEY_PEPPER=<third-random-value-at-least-32-characters>

HOST=127.0.0.1
PORT=8000

三个服务端密钥必须分别生成，长度都不能少于 32 个字符，也不能使用 change-me、replace-me 等弱值。已有 API 开发环境可以用下面的命令生成一个随机值；需要执行三次，并把每次结果分别放入三个设置。

bash
uv run python -c "import secrets; print(secrets.token_urlsafe(48))"
1

这条命令只生成文本，不会替你写入 .env。不要把生成结果提交到 Git。

理解这些值为什么必需 ​

设置作用错误配置的直接结果
SECRET_KEY签署访问令牌和 CSRF 令牌API 创建阶段拒绝弱值；更换后，现有登录状态失效
ENCRYPTION_KEY加密数据库中的敏感值API 创建阶段拒绝弱值；更换后，旧密文可能无法解密
MCP_KEY_PEPPER计算 MCP 密钥的服务端摘要API 创建阶段拒绝弱值；更换后，现有 MCP 密钥全部失效
DATABASE_URL指向共享关系数据库API 生命周期启动时无法完成数据库读取
CORS_ORIGINS列出允许携带浏览器凭据访问 API 的来源前端来源不匹配时，浏览器请求会被拦截
REPOSITORY_STORAGE_PATH保存远程仓库缓存后续克隆、拉取和缓存维护使用错误位置

OPAQUE_SERVER_SETUP 是密码登录协议的服务端长期材料。开发环境留空时，API 会在数据库中生成一份，并用 ENCRYPTION_KEY 加密。生产环境不会接受空值或弱值，必须预先提供稳定且格式正确的设置；当前源码没有可调用的项目命令负责生成它，因此部署流程需要另行生成并安全保存，不能照抄旧示例中的不存在函数。

在生产环境再收紧四项设置 ​

将 ENVIRONMENT 设为 prod 或 production 后，源码还会强制检查：

  • SESSION_COOKIE_SECURE=true；
  • SESSION_COOKIE_SAMESITE 只能是 lax、strict 或 none；
  • OPAQUE_SERVER_SETUP 必须存在，并通过强度检查；
  • ALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHS=false。

生产请求的 /api/ 和 /mcp 路径还必须使用 HTTPS。若前方有反向代理，应同时核对 PROXY_HEADERS 和 FORWARDED_ALLOW_IPS，只信任实际代理地址。

启动前后怎样确认 ​

在已经安装好依赖的 API 仓库中，先执行数据库升级，再启动服务：

bash
uv run ershu-db upgrade head
uv run ershu-api
1
2

这些命令是项目提供的入口，不表示已经在你的环境执行成功。配置正确时，应逐项看到以下结果：

  1. API 不再报告三个密钥过弱、生产 Cookie 不安全或本地路径开发开关错误。
  2. GET http://127.0.0.1:8000/health 返回 {"status":"ok"}。
  3. GET http://127.0.0.1:8000/api/v1/health/dependencies 中，顶层 status 为 ok，并且 database.ok 与 milvus.ok 都为 true。
  4. 若第 2 项成功但第 3 项为 degraded，只说明 API 进程存活；应继续修复数据库或 Milvus，而不是把部署视为就绪。

依赖检查当前不包含 Redis。要确认登录路径完整，还需实际完成一次登录请求；Redis 不可用时，登录限流会返回服务不可用错误。

源码位置 ​

  • core/src/ershu/core/config.py：共享设置、默认值、密钥强度和生产环境检查。
  • api/src/ershu/api/runtime_settings.py：API 设置、范围和生产环境检查。
  • api/src/ershu/api_main.py：启动流程、HTTPS、CORS、CSRF 与存活检查。
  • api/src/ershu/api/routes/health.py：数据库和 Milvus 依赖检查的返回结构。
  • api/src/ershu/api/services/auth/login_limits.py：Redis 登录限流。
  • api/.env.example：当前环境变量清单；其中生成 OPAQUE_SERVER_SETUP 的旧函数并不存在，不能直接采用。
  • api/pyproject.toml：ershu-api 命令和当前固定的 Core 依赖来源。
