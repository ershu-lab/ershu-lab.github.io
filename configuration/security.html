权限与安全：把信任边界配置清楚 ​

Ershu 会接触代码仓库、登录状态和模型凭据。安全配置的重点不是打开某个总开关，而是分别限制浏览器、仓库、Webhook、MCP 和管理员操作的信任范围。

保管四类服务端材料 ​

设置用途更换后的影响
SECRET_KEY签署访问令牌和 CSRF 令牌现有访问令牌和 CSRF 令牌失效
ENCRYPTION_KEY加密数据库中的模型密钥、仓库凭据和登录材料旧密文可能无法解密
MCP_KEY_PEPPER为 MCP 密钥摘要提供数据库之外的服务端材料所有现有 MCP 密钥失效
OPAQUE_SERVER_SETUP维持密码注册与登录协议的服务端身份更换后，现有密码记录可能无法继续登录

前三项必须互不相同，每项至少 32 个字符，并且不能使用源码列出的弱值。它们都应由部署平台的密钥管理能力注入，不能写入仓库、镜像或公开日志。

开发环境可以让 API 首次启动时把 OPAQUE_SERVER_SETUP 生成并加密保存到数据库。生产环境必须显式提供稳定的值。当前代码只检查生产值的存在和基本强度，真正使用时还要能解码为正确的 OPAQUE 服务端材料；一串任意长文本并不够。

保护浏览器会话 ​

生产环境至少需要以下设置：

dotenv
ENVIRONMENT=production
SESSION_COOKIE_SECURE=true
SESSION_COOKIE_SAMESITE=lax
CORS_ORIGINS=["https://ershu.example.org"]

具体域名必须换成真实前端来源。API 的浏览器保护分为三层：

  1. 生产环境下，/api/ 与 /mcp 请求必须表现为 HTTPS；否则返回 400。
  2. 携带会话 Cookie 的写请求必须同时提交有效的 X-Ershu-CSRF 请求头和 CSRF Cookie；请求带有 Origin 或 Referer 时，该来源还必须是当前站点或进入 CORS_ORIGINS，否则返回 403。
  3. 使用 Authorization: Bearer ... 的请求不依赖浏览器 Cookie，因此跳过 CSRF 检查，但仍要通过令牌认证和接口权限检查。

SESSION_COOKIE_SAMESITE=none 通常只适用于确实需要跨站 Cookie 的部署，并且仍要配合安全 Cookie 与准确的来源列表。不要用宽泛来源掩盖代理或域名配置错误。

若 HTTPS 在反向代理处终止，应只把实际代理地址写入 FORWARDED_ALLOW_IPS。API 依据请求方案判断是否为 HTTPS；转发头不可信或代理未正确传递方案时，会造成错误放行或错误拦截。

限制远程 Git 地址 ​

默认允许的仓库地址形式只有：

  • https://；
  • ssh://；
  • user@host:path 形式的 SCP 风格 SSH 地址。

http:// 和 git:// 只有在 ALLOW_INSECURE_GIT_URLS=true 时才会通过，file:// 只有在 ALLOW_FILE_GIT_URLS=true 时才会通过。这两个开关默认关闭，生产环境应继续关闭，除非已经评估并隔离相关风险。

GIT_ALLOWED_HOSTS 控制远程主机范围：

  • 列表为空时，主机仍要能解析，并且默认拒绝回环、私有、链路本地、多播、保留和未指定地址；
  • 列表非空时，不匹配的主机直接拒绝；
  • 精确列入或匹配通配规则的主机可以解析到私有地址，但回环、链路本地等地址仍然拒绝；
  • *.example.org 只匹配子域名，不匹配 example.org 本身。

生产环境应列出实际 Git 服务主机，避免使用 *。主机检查发生在后续克隆和拉取前；修改列表不会重新审查已经存在的缓存内容。

限制本地仓库路径 ​

本地路径满足以下任一条件时，Core 才把它作为受信任工作区：

  • 位于 REPOSITORY_STORAGE_PATH 管理的缓存目录内；
  • 位于 TRUSTED_LOCAL_PATHS 列出的目录或其子目录内；
  • 目录本身包含 .git。

ALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHS=true 是开发环境的兜底入口，只在没有配置受信任路径列表、且环境不是生产时生效。生产校验会拒绝打开它。管理员仍应只添加明确需要分析的路径；受信任表示允许读取，不表示内容本身可信。

分配仓库凭据 ​

仓库可以使用专用令牌、SSH 私钥或指向某个进程环境变量名称的凭据。Core 会优先使用仓库专用凭据；没有专用令牌时，GitHub 或 GitLab 仓库才会回退到全局 GITHUB_TOKEN 或 GITLAB_TOKEN。

令牌只在单次 Git 子进程环境中提供，临时凭据文件在命令结束后删除。数据库中的令牌和 SSH 私钥依赖 ENCRYPTION_KEY 解密。即便如此，也应遵循最小权限：只给需要的仓库读取权限，避免给写入或组织管理权限。

正确签署仓库 Webhook ​

启用 Webhook 前，项目管理者必须设置至少 16 个字符的密钥。每个请求需要三个头：

  • X-Ershu-Webhook-Timestamp：与服务端时间相差不超过 5 分钟；
  • X-Ershu-Webhook-Nonce：单次使用，最多 255 个字符，不能包含冒号或换行；
  • X-Ershu-Webhook-Signature：用 Webhook 密钥计算的 HMAC-SHA256 十六进制摘要。

签名消息必须按字节拼接：时间戳、一个 NUL 字节、Nonce、一个 NUL 字节、未经修改的原始请求正文。只签正文的旧做法不会通过。API 会把已使用的 Nonce 暂存到数据库，拒绝有效时间窗内的重复请求。

收紧 MCP 网络边界 ​

MCP 在生产环境还会检查：

  • MCP_BUILD_COMMIT 是准确的 40 位十六进制提交号；
  • 当前进程能读取已安装的 ershu-mcp 软件包版本信息；
  • MCP_ENABLE_DNS_REBINDING_PROTECTION=true；
  • MCP_ALLOWED_HOSTS 和 MCP_ALLOWED_ORIGINS 都不是空列表。

这些设置保护网络入口，项目和工具权限仍由 MCP 密钥范围、账号与项目成员关系决定。不要因为网络来源已允许，就跳过接口级授权。

上线前的可验证清单 ​

  • 使用四份独立、稳定的服务端材料，并在备份与恢复演练中确认旧密文仍能解密。
  • 通过 HTTPS 访问一个受保护的 API；HTTP 请求应被拒绝，HTTPS 响应应带有 HSTS 头。
  • 从允许的前端来源完成登录和一次写操作；去掉 CSRF 请求头后，同一写操作应返回 403。
  • 用不在 GIT_ALLOWED_HOSTS 中的地址创建或刷新仓库时，操作应在执行 Git 前被拒绝。
  • 重复发送同一时间戳、Nonce、正文和签名的 Webhook；第二次应被拒绝。
  • 用普通用户访问管理员系统设置接口，应返回 403；管理员访问才可读取。
  • 轮换 MCP_KEY_PEPPER 前先制定重新签发 MCP 密钥的计划，因为旧密钥不会继续有效。

这些是验收判据，不是本页声称已经执行过的测试结果。

源码位置 ​

  • core/src/ershu/core/config.py：密钥强度、独立性和生产本地路径检查。
  • core/src/ershu/core/security.py：访问令牌验证和敏感值加解密。
  • core/src/ershu/services/mcp_keys.py：MCP 密钥摘要与失效规则。
  • core/src/ershu/services/repositories/git_url_security.py：远程 Git 主机和地址范围检查。
  • core/src/ershu/services/repositories/workspaces.py：协议、凭据选择和临时凭据处理。
  • core/src/ershu/tools/readonly_repository/workspace.py：本地仓库信任规则。
  • api/src/ershu/api_main.py：HTTPS、来源、CSRF 和 HSTS 处理。
  • api/src/ershu/api/web_security.py：Cookie 与 CSRF 令牌。
  • api/src/ershu/api/services/opaque_auth.py：OPAQUE 设置的初始化、存储和读取。
  • api/src/ershu/api/services/repositories/triggers.py：Webhook 签名、时间窗和防重放。
  • mcp/src/ershu/mcp/runtime_settings.py：MCP 生产网络校验。
