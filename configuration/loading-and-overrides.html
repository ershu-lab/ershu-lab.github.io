配置加载与覆盖：确认最终生效的值 ​

同一个设置可能同时出现在默认值、.env、进程环境和数据库中。本页说明最终值从哪里来，以及修改后何时生效。

先区分两类设置 ​

Ershu 的后端设置分为两类：

  1. 启动设置：由设置类在进程内创建一次并缓存。修改环境变量后，需要重启对应进程。
  2. 可在线覆盖设置：先读取环境值，再允许数据库中 runtime.<name> 这一行覆盖。服务刷新运行时设置后，新操作会使用新值。

数据库覆盖不是对 .env 的改写。删除覆盖行后，设置会回到进程启动时读取的环境值，而不是恢复某个额外副本。

优先级从低到高 ​

优先级来源说明
1设置类默认值只在没有其他来源时使用
2.env设置类声明读取名为 .env 的文件
3进程环境变量部署平台注入的值覆盖同名 .env 值
4数据库运行时设置仅适用于已登记的运行时设置；键名为 runtime.<name>

API 的 get_api_settings() 和 Core 的 get_settings() 都使用进程内缓存。因此，修改非运行时环境变量，例如 DATABASE_URL、REDIS_URL、CORS_ORIGINS 或任何密钥后，必须重启使用它的进程。

API 自己允许在线覆盖哪些值 ​

API 进程会读取 10 项 Core 运行时设置，再增加 1 项自己的聊天流式票据时长。

设置名环境变量允许值新值用于
run_queue_lease_timeout_secondsRUN_QUEUE_LEASE_TIMEOUT_SECONDS300 至 86400新的恢复扫描和心跳间隔
analysis_run_retention_countANALYSIS_RUN_RETENTION_COUNT1 至 10000任务完成或维护清理时的项目历史保留量
search_index_batch_sizeSEARCH_INDEX_BATCH_SIZE100 至 20000新的索引重建批次
git_command_timeout_secondsGIT_COMMAND_TIMEOUT_SECONDS10 至 3600后续 Git 命令和缓存锁等待
repository_storage_pathREPOSITORY_STORAGE_PATH非空字符串，最多 255 个字符后续仓库缓存访问
trusted_local_pathsTRUSTED_LOCAL_PATHS最多 50 个字符串后续本地工作区授权
allow_dev_open_local_repository_pathsALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHS布尔值后续本地工作区授权
git_allowed_hostsGIT_ALLOWED_HOSTS最多 50 个字符串后续远程仓库地址检查
allow_insecure_git_urlsALLOW_INSECURE_GIT_URLS布尔值后续仓库地址检查
allow_file_git_urlsALLOW_FILE_GIT_URLS布尔值后续仓库地址检查

这里的“后续”很重要。例如，调整仓库路径不会移动现有缓存，调整票据时长也不会改写已签发票据。

管理接口为什么会显示 48 项 ​

管理员接口 GET /api/v1/admin/system-settings 汇总三组定义：

  • 10 项 Core 运行时设置；
  • 37 项 Worker 运行时设置；
  • 1 项 API 运行时设置。

API 负责校验并保存全部 48 项，也会在返回值中给出 environment_value、当前 value 和 source。但 API 进程只把 Core 与 API 定义应用到自己；Worker 必须由自己的刷新流程读取 Core 与 Worker 定义。看到管理接口保存成功，不代表每个正在运行的 Worker 已经刷新。

管理员可以通过以下三个端点管理覆盖：

操作端点结果
读取GET /api/v1/admin/system-settings返回所有定义、环境值、当前值和来源
更新PATCH /api/v1/admin/system-settings校验后写入数据库，并记录审计日志
重置DELETE /api/v1/admin/system-settings/{name}删除该设置的数据库覆盖，回到环境值

这些端点只允许管理员账号访问。传入未知名称、错误类型、越界整数或过长列表时，请求会以输入错误结束，不会保存一半有效、一半无效的含糊状态。

修改后多久生效 ​

API 在启动时刷新一次，之后每 30 秒读取一次数据库覆盖。管理接口在写入或删除后会立即重新读取并返回当前状态。因此，API 侧的新操作通常能立即看到刚保存的 Core/API 值；其他 API 实例最迟在下一次正常刷新后看到。

周期刷新失败时，API 会记录错误并继续下一轮，不会主动退出。数据库里如果被外部工具写入无法解码或越界的值，刷新会失败；应通过管理接口修复或删除对应 runtime.<name> 行。

Worker 的生效时间由 Worker 自己的刷新点决定。不要用 API 的 30 秒周期推断 Worker 一定在相同时间更新。

用返回值确认谁在生效 ​

  • source 为 environment：当前没有数据库覆盖，value 应与 environment_value 相同；
  • source 为 database：数据库覆盖正在生效，两个值可以不同；
  • 重置后再次读取：source 应回到 environment；
  • 修改非运行时环境变量后：只有重启对应进程，缓存设置才会重建。

源码位置 ​

  • core/src/ershu/core/config.py：.env 声明、Core 设置和缓存入口。
  • core/src/ershu/services/runtime_settings.py：Core 运行时定义、数据库键名、值校验、刷新和覆盖应用。
  • core/src/ershu/services/worker_runtime_contract.py：37 项 Worker 管理契约。
  • api/src/ershu/api/runtime_settings.py：API 设置、流式票据定义和 API 刷新入口。
  • api/src/ershu/api/services/system_settings.py：48 项设置的汇总、来源标记、更新与重置。
  • api/src/ershu/api/routes/system_settings.py：管理员端点与权限依赖。
  • api/src/ershu/api_main.py：启动刷新和每 30 秒一次的 API 刷新循环。
  • worker/src/ershu/workers/runtime_settings.py：Worker 应用 Core 与 Worker 运行时设置的入口。
