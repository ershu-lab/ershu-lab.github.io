认识 Ershu：能力、边界和适用场景 ​

Ershu 是一套自行部署的代码理解与上下文服务。它把一个项目下的多个 GitHub、GitLab 或受信任本地仓库作为整体分析，生成文档、检索索引和代码关系，再通过网页、HTTP API 与 MCP（模型上下文协议）提供结果。

MCP 是开发智能体读取外部工具和数据的一种标准接口。在 Ershu 中，它是只读查询入口，不负责修改仓库。

一次分析会留下什么？ ​

结果用途从哪里使用
仓库树和文件事实确认路径、文件类型和当前提交网页、API、MCP
结构化项目文档按主题理解模块与流程网页、API、MCP
词法与语义索引按名称、文本或含义查找代码网页、API、MCP
知识关系查看符号和文件之间的联系网页、API、MCP
分析记录与检查点跟踪阶段、用量、结果和失败位置网页、API

Worker 只通过受限的只读工具读取分析工作区，不执行仓库脚本。生成文档需要已经配置并启用的模型通道；确定性的仓库事实和部分索引流程不等同于模型生成。

它怎样融入日常工作？ ​

  1. 管理员创建首个账号，配置模型通道和项目访问权限。
  2. 项目成员添加仓库，并先运行一次覆盖全部有效仓库的全项目分析。
  3. Worker 在后台准备只读工作区，提取事实并生成项目级结果。
  4. 成员在网页阅读文档、搜索和查看关系；开发智能体通过受限 MCP 密钥查询同一项目。
  5. 后续仓库提交可以触发增量分析。Cron 轮询和签名 Webhook 都由 API 侧接收，实际分析仍交给 Worker。

第一次分析必须是全项目分析。没有这份基线时，API 会拒绝增量任务，避免把局部结果误当成完整项目视图。

哪些人适合使用？ ​

  • 维护由多个仓库组成、需要统一项目视图的团队；
  • 需要理解陌生代码、追踪实现来源或核对模块边界的开发者；
  • 需要给开发智能体提供可控、可追溯上下文的负责人；
  • 希望在自己的基础设施中保管仓库凭据、项目权限和模型设置的组织。

使用前要知道的边界 ​

  • 当前项目需要自行部署，尚不能仅靠公开软件包完成全套安装；组合仓库和后端模块仍引用私有 Git 源。
  • Ershu 生成的是帮助理解代码的材料，不替代源码、测试和人工评审。来源冲突时应回到当前代码核对。
  • /health 是进程存活检查，不代表所有外部依赖都已就绪。数据库、Milvus、模型通道和 Worker 需要分别确认。
  • API 创建任务后只会把任务放入队列；没有运行中的 Worker，任务不会完成。
  • 语义检索依赖可用的 Milvus 和嵌入模型。语义模式失败时不会悄悄改成词法搜索；混合模式才可能明确报告回退。
  • 本地仓库只允许管理员配置，并且路径必须进入受信任范围。

如果这些前提符合你的环境，请继续阅读特性详解；准备实际部署时，从基础配置开始。

事实来源：五个模块的入口、仓库结构类型、运行创建与队列测试、只读工具安全测试，以及 Ershu MCP 项目概览。
