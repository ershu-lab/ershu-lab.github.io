Ershu 是什么 ​

Ershu 是一套自行部署的代码理解服务。你把一个产品的前端、后端、微服务和共享库放进同一个项目，Ershu 读取这些仓库，整理出内部 Wiki、代码索引、项目关系和接口约定。

团队通过网页阅读、搜索和查看关系。AI 编程工具通过 MCP 查询同一份结果。MCP 是一种让 AI 客户端调用外部工具的通用协议，Ershu 提供的是只读查询，不会通过 MCP 修改仓库。

它与常见做法有什么不同 ​

做法擅长什么容易缺少什么
手写 Wiki记录背景、决策和团队经验需要持续维护，容易与当前提交脱节
仓库内搜索快速找到已知符号和文字很难给出跨仓库项目全貌
让 AI 直接扫描工作区针对当前任务即时读代码每次会话都可能重新建立上下文，范围也受当前工作区限制
Ershu保存项目级分析结果，供网页和 MCP 重复使用仍需要部署、模型配置和第一次完整分析

这些做法可以一起使用。手写文档适合记录“为什么”，Ershu 更适合从当前代码整理“现在是什么”。精确行为最终仍由源码和测试决定。

一次完整分析会留下什么 ​

结果你可以用它做什么
项目 Wiki按主题阅读模块、流程、配置和仓库说明，并从引用回到源码
仓库目录与代码索引按路径、语言和符号浏览代码，不必先克隆到每位读者的电脑
关键词与向量索引按精确名称或含义搜索代码、文档、接口和配置
项目知识图谱查看仓库、目录、符号、调用和依赖之间的候选关系
接口约定查询公开接口、消费者关系、数据结构和不同版本之间的变化
运行记录查看分析阶段、警告、模型用量、生成结果和失败位置

文档由模型参与生成。目录、代码索引、接口事实和一部分关系来自确定性分析。Ershu 会在结果中保留提交、新鲜度、来源级别、覆盖范围和截断信息，让调用方知道哪些内容可以直接使用，哪些仍要回到源码确认。

五个组件怎样配合 ​

  • Core 保存共用的数据、权限、任务状态、查询能力和数据库升级记录。它不是单独的服务。
  • API 为网页提供登录、项目管理、任务、文档、搜索、聊天和后台管理接口。
  • Worker 领取任务，读取仓库并生成文档、索引、关系和接口事实。
  • MCP 把已经保存的项目知识提供给 AI 客户端。
  • Frontend 是团队使用的网页工作区。

PostgreSQL 保存账号、项目、权限、任务和文档等业务数据。Milvus 保存向量索引。Redis 用于登录限流和轮询协调，不是 Worker 的持久任务队列。

Python 安装可以按组件选择 ​

ershu 是统一安装入口。默认只安装 Core，需要哪个进程就选择哪个附加项：

命令安装内容
pip install ershuCore 和数据库升级命令 ershu-db
pip install "ershu[api]"Core 与 API
pip install "ershu[mcp]"Core 与 MCP
pip install "ershu[worker]"Core 与 Worker
pip install "ershu[all]"Core、API、MCP 与 Worker

UV 项目可以使用 uv add ershu 或 uv add "ershu[all]"。完整部署还需要 PostgreSQL、Redis、Milvus 等基础设施和单独发布的前端，因此第一次部署更适合直接使用 ershu Release 中的部署压缩包。

从代码到可用结果 ​

  1. 管理员创建账号，配置语言模型和向量模型通道。
  2. 项目负责人创建项目，把属于同一产品的仓库加进来。
  3. 第一次运行覆盖全部活动仓库，建立项目基线。
  4. Worker 读取仓库，写入 Wiki、索引、关系、契约和运行记录。
  5. 团队在网页使用这些结果，AI 客户端通过 MCP 按需读取。
  6. 代码变化后，通过新运行、计划轮询或签名 Webhook 更新项目事实。

自动事实刷新不会顺带重写 AI 文档。需要更新文档时，应创建包含文档生成的分析运行。

使用前先知道这些边界 ​

  • 只有 API 没有 Worker 时，任务可以入队，但不会完成。
  • 语义搜索需要 Milvus、可用的向量模型通道和已经建好的向量索引。关键词搜索不依赖向量模型。
  • 关系、影响面和静态运行路径用于缩小候选范围，不等于完整的动态调用证明。
  • 本地仓库路径必须对实际运行 API、Worker 或 MCP 的主机可见，并进入受信任范围。
  • 自行部署让团队掌握服务和存储位置。模型服务是否位于内网，仍由部署者的模型通道决定。

想判断不同角色能得到什么，请看使用场景。准备动手时，从单机快速部署开始。
