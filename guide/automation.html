自动跟进仓库更新 ​

Ershu 有两种自动检查仓库提交的方式：独立 Poller 按 UTC Cron 计划拉取仓库，或外部系统调用签名 Webhook。两条路径都会先判断提交是否已经分析或排队，只有发现需要处理的提交才创建事实刷新任务。

自动触发只更新目录、代码索引、知识关系和搜索索引，不会重新生成 AI 文档。需要文档跟上新提交时，应另行发起支持文档生成的分析任务。

先选择触发方式 ​

方式适合什么情况额外依赖成功信号
计划轮询仓库系统不能主动通知 Ershu，或希望由 Ershu 控制检查节奏持续运行的 ershu-api-poller 和 RedisPoller 审计记录出现，响应结果为 queued 或带明确原因的 skipped
签名 Webhook外部系统能在提交发生时发送自定义 HTTP 请求能按 Ershu 格式计算 HMAC 的发送端Webhook 返回 HTTP 202，正文为 queued 或带原因的 skipped
手动轮询配置后立即验证仓库访问和变化判断已登录且有项目管理权限手动轮询接口返回 HTTP 202 和可解释结果

不论哪种方式，实际工作都由 Worker 从 PostgreSQL 队列领取。Worker 未运行时，queued 只表示任务已经入队。

配置计划轮询 ​

在仓库触发设置中先填写 poll_cron，再启用 poll_enabled。计划必须是合法的五段 Cron 表达式，并统一按 UTC 解释。例如，0 * * * * 表示每个 UTC 整点检查一次。

API 对应的管理路径是：

text
PATCH /api/v1/projects/{project_id}/repositories/{repository_id}/triggers
1

请求含有敏感的登录状态与 CSRF 保护，通常应通过网页设置。启用时若没有计划，API 会拒绝保存。

随后单独运行 Poller。下面是建议命令，本任务没有在你的环境中执行它：

bash
uv run ershu-api-poller
1

Poller 的默认行为是每 30 秒扫描一次，到期仓库每批最多 100 个。它使用 Redis 的可续租锁，默认租期 120 秒，同一时刻只有取得锁的实例执行扫描。相关范围见环境变量参考。

想立即做一次诊断性扫描时，可以使用建议命令：

bash
uv run ershu-api-poller --once
1

命令以退出码 0 结束只说明本轮进程没有未处理错误。是否发现更新，要继续看仓库的最近轮询时间、审计记录和新任务状态。

配置签名 Webhook ​

在仓库触发设置中先保存一个至少 16 个字符的 webhook_secret，再启用 webhook_enabled。读取设置时只会返回 has_webhook_secret，不会回传密钥原文。

Webhook 地址为：

text
POST /api/v1/webhooks/repositories/{repository_id}
1

请求正文是 JSON，可包含：

字段约束用途
branch可省略指定要记录的分支
commit_sha可省略；必须是 40 或 64 位十六进制指定要刷新的准确提交
event可省略；最多 64 个字符在结果和审计记录中说明触发原因

发送端必须保留最终发送的原始正文字节，并构造三个请求头：

请求头内容
X-Ershu-Webhook-Timestamp当前 Unix 时间；服务端允许与数据库时间相差最多 300 秒
X-Ershu-Webhook-Nonce本次请求的唯一值；最多 255 个字符，不能含冒号或换行
X-Ershu-Webhook-Signature下述内容的 HMAC-SHA256 小写十六进制摘要

签名消息必须严格按字节拼接：

text
UTF-8(timestamp) + NUL + UTF-8(nonce) + NUL + raw_request_body
1

HMAC 密钥就是仓库中保存的 webhook_secret。签名覆盖的是最终发送字节；计算后重新格式化 JSON 会导致认证失败。相同 nonce 在保护窗口内再次使用也会被拒绝。

以下请求只展示正文形状，不包含可直接使用的签名，因此不能原样执行：

json
{
  "branch": "main",
  "commit_sha": "<40-or-64-character-commit>",
  "event": "push"
}

读懂触发结果 ​

成功通过认证和参数校验的 Webhook、手动轮询都会返回 HTTP 202。正文的 status 决定下一步：

status常见 reason含义
queuedwebhook、poll_detected_change 或发送端给出的事件已创建或复用需要 Worker 处理的事实刷新任务
skippedcommit_already_analyzed该分支和提交的事实已经是当前状态
skippedcommit_already_queued相同仓库、分支和提交已有任务在队列中
skippedlocal_workspace_dirty本地工作区有未提交修改，轮询不会把它当作可复现提交刷新
skippedrepository_has_no_git_commit工作区没有可识别的 Git 提交

queued 结果会带 run_id。继续在运行页面或 MCP 的 get_run_status 中观察它；只有进入完成状态，并且仓库的目录、代码、关系与搜索状态已更新，才算本次自动刷新结束。

上线前做一次闭环验证 ​

下面是建议检查步骤，不代表已经替你执行：

  1. 保存触发设置，再读取一次，确认启用状态、Cron 和 has_webhook_secret 符合预期。
  2. 对一个已知提交执行手动轮询，或发送一条正确签名的测试 Webhook。
  3. 确认 HTTP 结果是 queued，或是原因符合预期的 skipped。
  4. 对 queued 结果确认 Worker 领取了对应 run_id。
  5. 等待任务完成，再检查仓库提交和各层新鲜度。
  6. 重发同一提交，确认返回 commit_already_analyzed 或 commit_already_queued，而不是产生无止境的重复任务。

如果计划一直不执行，先确认 ershu-api-poller 是独立运行的，再检查 Redis、UTC Cron 和仓库凭据。API Web 进程本身不会代为执行计划。

主要源码位置：api/src/ershu/api/poller.py、api/src/ershu/api/services/repositories/triggers.py、api/src/ershu/api/routes/projects/repositories.py、core/src/ershu/services/runs/fact_refresh.py。
