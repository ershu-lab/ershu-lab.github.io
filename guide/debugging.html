定位分析与检索问题 ​

排查 Ershu 时，先区分“进程活着”“依赖可用”“任务完成”和“结果足够新”这四件事。它们有不同的检查入口，不能只凭一个绿色健康页判断整个系统正常。

先用最短路径定位层级 ​

第 1 层：确认进程，而不是整个系统 ​

下面是建议检查命令，本任务没有在你的部署中执行：

bash
curl -fsS http://127.0.0.1:8000/health
curl -fsS http://127.0.0.1:8000/api/v1/health/dependencies
curl -fsS http://127.0.0.1:8001/health

MCP get_server_info凭据可用，协议调用成功，并返回当前工具和构建身份某个项目的索引一定完整
Worker 进程持续运行启动校验和结构化解析器自检通过一定能完成某个具体任务

Worker 没有 HTTP 健康端点。它启动时会验证 ENCRYPTION_KEY、分析注册表、数据库连接和结构化解析器；其中任何一项失败都可能让进程退出。最终仍要用一条实际排队任务能否推进来验证。

第 2 层：任务排队但不动 ​

先打开运行详情，记录运行编号、当前状态、最后事件和错误，不要立刻重建索引。

现象可能的边界可观察的下一步
一直停在排队Worker 没运行、连错数据库，或无法领取任务确认 Worker 与 API 使用同一 DATABASE_URL；Worker 日志应出现启动和轮询信息
运行后很快失败密钥、仓库凭据、模型通道、解析器或外部依赖失败查看运行错误和 Worker 同期日志；错误应指向失败阶段
等待用户输入已开启分析提问，且任务正在等待回答在运行页面回答问题，或等待配置的超时处理
完成但带警告文档已发布，但搜索索引等后续步骤降级查看警告与各层状态，不要把“完成”理解为所有索引都完整
定时检查没有产生任务Poller 没单独运行、Cron 未到期、Redis 租约未取得，或提交已是当前状态查看最近轮询时间与 repository.poll_scheduled 审计记录

队列租约超时默认 600 秒。Worker 会恢复失去有效租约的中断任务，但不要靠缩短租约掩盖一个持续崩溃的 Worker。

第 3 层：仓库无法准备 ​

远程仓库先检查登记的 URL、默认分支和凭据。私有仓库可以使用仓库自身保存的凭据，也可以按仓库类型使用 GITHUB_TOKEN 或 GITLAB_TOKEN。Git 命令默认最多运行 120 秒。

本地仓库还要同时满足：

  • 路径位于运行进程能访问的文件系统；
  • 路径落在 TRUSTED_LOCAL_PATHS 内；
  • 生产环境没有启用开发用宽松开关；
  • 如果由 Worker 分析、由 MCP 读取，两台主机都能看到登记的路径。

轮询遇到未提交修改会返回 local_workspace_dirty，没有 Git 提交会返回 repository_has_no_git_commit。这些是有意的跳过，不是队列故障。

第 4 层：搜索结果为空或降级 ​

先查看响应中的 mode、degraded、degradation_reason、retrieval_sources 和 fallback_used。

  • keyword 只走词法结果。
  • semantic 只接受语义结果。没有嵌入通道、可用索引或 Milvus 查询时，它会明确失败，不会把词法结果伪装成语义命中。
  • hybrid 组合语义与词法结果。语义分支不可用时，它可以返回词法结果，但会把降级和回退写进响应。

再查看仓库或运行结果中的 search_index_status。indexing 表示后台索引仍在进行；仓库的 keyword_only、degraded，以及运行结果的 degraded、unavailable，都表示不能把结果当作完整语义检索。后台搜索索引开启时，分析任务可能先完成，索引稍后才完成。

如果只有文档命中，响应可能标记 documents_fallback。这类结果适合导航，不是实现证据，应继续用源码读取核对。

第 5 层：关系或变更面看起来不完整 ​

关系查询和变更面查询都受范围限制。检查：

  • data_status 是 available、partial、stale 还是 unavailable；
  • result_status 是否因为数据不可用而无法判断；
  • 仓库覆盖范围、未命中仓库、查询 limit 和截断标记；
  • 结果是 direct 还是 related，以及置信度；
  • 仓库最近观察到的提交是否与索引提交一致。

“没有返回”不总等于“没有关系”。数据不可用时，正确结论是未知；结果被截断时，正确结论是当前返回了一组有界候选。

第 6 层：文档与源码冲突 ​

按以下顺序判断：

  1. 查看文档对应的分支、提交和新鲜度。
  2. 查看 authority。AI 生成文档属于 secondary，源码和结构化契约属于 source_derived。
  3. 用目录和代码索引定位路径。
  4. 用 read_code_context 或当前本地源码核对精确字段、默认值和行为。

源码与文档冲突时，以当前源码为准。refresh_repository_facts 只刷新四类事实，不会修正文档，因此不要把一次事实刷新误当作文档已经重写。

带着证据报告问题 ​

一份可复现的问题记录至少包含：

  • 模块和运行入口；
  • 项目、仓库和运行编号，但不包含密钥；
  • 仓库分支、提交和新鲜度；
  • 第一个失败状态或错误类别；
  • API 依赖检查中数据库与 Milvus 的结果；
  • Worker、API 或 MCP 同一时间段的相关日志；
  • 查询模式、降级、回退、覆盖范围和截断信息；
  • 能稳定重现的最短步骤。

不要附上 SECRET_KEY、ENCRYPTION_KEY、MCP_KEY_PEPPER、MCP 密钥、Webhook 密钥或仓库访问凭据。
