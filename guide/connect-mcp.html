把 Ershu 接入 MCP 客户端 ​

Ershu 的 MCP 服务是面向开发智能体的只读入口。它不修改仓库，也不负责生成文档；它读取 Core 中的项目、权限、文档、索引和关系查询，并为每次请求应用用户权限与 MCP 密钥范围。

本页不绑定某一款客户端。不同客户端的配置字段不同，但都需要相同的连接信息。

接入前确认三件事 ​

  1. MCP 进程正在运行，默认地址是 http://127.0.0.1:8001/mcp/。
  2. 你已经能在 Ershu 网页中读取目标项目。密钥不会扩大你的项目权限。
  3. 目标仓库已有可用事实。目录可以按当前源码读取；代码索引、关系和文档的完整程度取决于分析与刷新状态。

可以先打开 http://127.0.0.1:8001/health。返回 {"status":"ok"} 只说明进程存活，不代表数据库、权限或工具调用已经成功。

创建最小权限密钥 ​

在 Ershu 网页的 MCP 密钥管理页创建密钥时，需要填写名称，并选择以下一种范围：

  • 仅允许一个或多个明确项目；
  • 允许当前用户可读的全部项目。

还可以设置未来的过期时间。更稳妥的默认做法是只选当前任务需要的项目，并设置到期时间。服务只在创建响应中返回完整密钥；之后的列表只保留前缀、范围、到期时间和使用记录，因此应在创建时保存到客户端的密钥存储中。

密钥被撤销、过期，或原用户失去项目读取权限后，调用会被拒绝。创建和撤销都会写入审计记录。

填写客户端连接信息 ​

把以下信息映射到客户端的 Streamable HTTP 配置。字段名以你的客户端文档为准，不要直接假定它使用某个固定 JSON 结构。

信息值
传输方式Streamable HTTP
服务地址http://127.0.0.1:8001/mcp/
请求头Authorization: Bearer <MCP_KEY>

生产环境应使用 HTTPS，并把 /mcp/ 原样转发到 MCP 进程的 8001 端口。外部 Host 和 Origin 必须进入 MCP_ALLOWED_HOSTS 与 MCP_ALLOWED_ORIGINS。不要把 MCP 请求发送到 API 的 8000 端口。

用 get_server_info 完成第一次验证 ​

连接后先调用 get_server_info。成功结果包含：

  • service，当前应为 ershu-mcp；
  • 已安装的包版本；
  • 构建使用的完整提交号；
  • identity_status；
  • 当前注册的工具名。

生产进程只有在包版本可读、MCP_BUILD_COMMIT 是完整 40 位提交号时才允许启动。开发环境可以没有这两项，此时 identity_status 会是 unavailable，不能把它当作已核验的构建身份。

当前服务应列出 27 个工具。若连接成功但没有工具，或清单与预期构建不一致，应先检查服务版本和代理路径，不要继续依据不明版本开展工作。

一条可靠的项目阅读顺序 ​

项目参数可以使用 UUID、slug 或唯一的可读名称。名称有歧义时改用 slug 或 UUID。

  1. 用 list_projects 发现当前密钥可见的项目。
  2. 用 resolve_project 确认项目引用，再用 list_project_repositories 取得仓库编号和新鲜度。
  3. 用 get_project_overview 建立项目级方向，用 list_repository_documents 和 list_document_sections 选择要读的章节。
  4. 用 list_repository_tree 和 list_repository_code_index 找到源码路径和符号。
  5. 用 find_project_change_surface 或 trace_project_runtime_flow 缩小范围。
  6. 最后用 read_code_context 读取关键源码，核对精确行为。

文档结果的 authority 可能是 secondary，适合导航和解释；源码、契约与结构化事实标为 source_derived，更适合支撑精确结论。任何时候都要同时查看提交、新鲜度、覆盖范围和截断标记。

27 个工具怎样分工 ​

目的工具
服务与项目发现get_server_info、list_projects、resolve_project、list_project_repositories
更新事实并跟踪任务refresh_repository_facts、get_run_status
阅读项目文档get_project_overview、list_repository_documents、list_document_sections、get_document、get_document_section
浏览源码与索引list_repository_tree、list_repository_code_index、read_code_context
搜索与关系分析search_project_context、query_internal_api、query_project_graph、find_project_change_surface、trace_project_runtime_flow
读取消费者契约list_project_contracts、get_consumer_contract、list_public_interfaces、get_public_interface、get_contract_schema、query_consumer_contracts、diff_consumer_contracts、suggest_consumer_work

分页工具的 limit 通常是 1 到 100，偏移量从 0 开始。目录深度最多为 10，单次目录结果最多保留 500 项；源码读取单次最多 400 行。消费者契约查询的实际服务上限是 50。这些边界用于控制上下文大小，不表示结果天然完整。

什么时候刷新事实 ​

如果仓库的新鲜度显示过期，并且当前用户有项目维护权限，可以调用 refresh_repository_facts。它只排入以下四类更新：

  • 目录树；
  • 代码索引；
  • 知识关系；
  • 搜索索引。

它不会生成或改写 AI 文档。工具返回任务编号后，用 get_run_status 观察 queued、running、完成或失败状态。状态查询本身不会创建新任务。

常见失败怎样判断 ​

现象先检查什么
401 或认证失败请求头是否精确使用 Bearer；密钥是否过期、撤销或复制不完整
项目找不到密钥范围、用户项目权限，以及名称是否有歧义
浏览器能开 /health，客户端仍连不上客户端是否使用 /mcp/，代理是否保留路径，Host 和 Origin 是否允许
搜索结果降级返回的检索模式、degraded、fallback_used 和搜索索引状态
关系结果很少data_status、覆盖范围、限制和截断标记；有界候选不是完整清单
文档与源码不一致先看文档提交和 authority，再用 read_code_context 核对当前源码

健康页只是第一步。真正可用时，客户端能认证调用 get_server_info，能列出一个确实有权限的项目，并能从该项目读取带仓库提交信息的目录或源码结果。
