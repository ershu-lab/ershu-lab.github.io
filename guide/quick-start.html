本页内容

把 Ershu 启动到可登录状态 ​

本页面向已经取得内部组件访问权限的维护者。目标不是完成分析，而是把基础设施、API、Worker 和前端启动到可以继续配置的状态。

当前不能从公开包源直接安装

组合仓库和后端模块仍从私有开发源取得 Core 等依赖。没有对应的 Git 和 SSH 权限时，uv sync --all-extras --frozen 会在取得依赖时失败。目前没有可替代的公开安装命令。

下面的命令来自当前仓库清单和 README。它们说明应如何操作，不代表已经在你的机器上执行成功。

前置条件 ​

开始前确认你具备：

  • Python 3.14；
  • UV；
  • Docker 和 Docker Compose；
  • Node.js 24；
  • 对当前私有组件源的访问权限；
  • 与后端版本匹配的独立 frontend 仓库检出。

Core 是共享包，不单独启动进程。网页完成第一次分析至少需要 PostgreSQL、Milvus 等基础设施、API、Worker 和前端。MCP 和仓库轮询进程按使用场景另行启动。

第 1 步：启动基础设施 ​

在 ershu 组合仓库中复制 Compose 配置：

bash
cp .env.compose.example .env.compose
1

打开 .env.compose，替换示例中的 PostgreSQL 和 MinIO 密码，然后启动服务：

bash
docker compose --env-file .env.compose up -d
docker compose --env-file .env.compose ps
1
2

成功后，ps 列出的 PostgreSQL、Redis、Milvus、etcd 和 MinIO 服务应处于运行状态。如果其中一项反复重启，先查看对应容器日志，不要继续执行数据库迁移。

第 2 步：准备后端配置 ​

复制当前配置模板：

bash
cp .env.example .env
1

按文件注释替换示例密码和密钥，并确认数据库、Redis 与 Milvus 地址指向上一步启动的服务。模型名称、模型 API Key 和模型地址不要写进 .env；它们稍后在网页的模型通道中配置。

完成后，你应有一份仅供本地环境使用的 .env，其中不再保留准备用于真实环境的示例密钥。

第 3 步：安装后端并执行迁移 ​

只有具备私有组件源访问权限时，才能执行：

bash
uv sync --all-extras --frozen
uv run ershu-db upgrade head
1
2

成功判据是两条命令都以退出码 0 结束。若第一条命令无法取得 Core 或其他 Ershu 包，这是当前公开安装限制，不应通过删除锁文件或改用未经核实的包来绕过。

第 4 步：启动 API 和 Worker ​

分别打开两个终端，并让进程保持运行。

终端 A：

bash
uv run ershu-api
1

终端 B：

bash
uv run ershu-worker
1

在浏览器访问 http://127.0.0.1:8000/health。API 可用时会返回状态为 ok 的响应。这个地址只确认 API 进程存活；/api/v1/health/dependencies 还会检查数据库和 Milvus，但不检查 Redis。

Worker 当前没有网页健康检查。进程应持续运行且不立即退出；稍后的第一次运行能从队列继续推进，才是最终验证。

如果需要 MCP，再开一个终端运行：

bash
uv run ershu-mcp
1

如果需要按仓库计划自动检查提交，再单独运行：

bash
uv run ershu-api-poller
1

这两个进程不是完成首次网页分析的前置条件。

第 5 步：启动前端 ​

进入独立的 frontend 仓库：

bash
cp .env.example .env.local
npm ci
npm run dev
1
2
3

开发服务器默认使用 http://localhost:3000，并把 /api 转发到 http://localhost:8000。如果 API 在其他地址，修改 .env.local 中的 VITE_DEV_API_PROXY 后重启开发服务器。

成功后，打开 http://localhost:3000：

  • 全新数据库会跳转到首次管理员设置页；
  • 已经存在用户的数据库会跳转到登录页；
  • 页面若持续报网络错误，说明前端尚未连接到 API。

现在可以继续创建第一个项目。
