把快速部署改成生产部署 ​

快速部署已经使用发布包、PyPI 和 systemd。生产环境沿用同一套目录和服务，不需要重新改成源码安装。上线前还要补齐域名与 TLS、正式配置、备份、监控和访问控制。

推荐结构 ​

API、MCP 和 Worker 可以先放在同一台可信主机，也可以分开运行。它们必须连接同一个 PostgreSQL；启用向量检索时，也要连接同一个 Milvus 数据库。

部署包中的 systemd 文件面向单机结构。拆分到多台主机时，请按同样的账号、配置和目录边界分别建立服务。

1. 只安装发布版本 ​

每个组合放在独立目录：

text
/opt/ershu/releases/<tag>
1

先核对 GitHub Release 中的 SHA256SUMS，再运行部署包内的安装脚本：

bash
sudo bash deploy/systemd/install.sh --uv-bin "$(command -v uv)"
1

脚本从 versions.env 读取组合版本，并从 PyPI 安装准确的 ershu[all]。组件后续可以使用不同版本，运维仍只需要安装这个组合指定的 ershu 版本。

/opt/ershu/current 指向当前版本。配置和数据放在版本目录外，所以切换发布版本不会覆盖密钥、数据库或仓库缓存。

2. 使用生产配置 ​

后端配置在 /etc/ershu/.env，基础设施配置在 /etc/ershu/compose.env。至少检查这些值：

设置生产要求
ENVIRONMENT使用 production
HOST、MCP_HOST通常继续监听 127.0.0.1，只让反向代理对外开放
SESSION_COOKIE_SECURE使用 true
CORS_ORIGINS只列出实际前端的 HTTPS 来源
PROXY_HEADERS反向代理部署时使用 true
FORWARDED_ALLOW_IPS只信任真实代理地址
OPAQUE_SERVER_SETUP保留第一次部署生成的值，不能在升级时重新生成
SECRET_KEY、ENCRYPTION_KEY、MCP_KEY_PEPPER使用三个不同的随机值，并放进密钥管理系统
MCP_BUILD_COMMIT填写当前 MCP 版本对应的完整 40 位提交号
MCP_ALLOWED_HOSTS、MCP_ALLOWED_ORIGINS只允许实际域名和 HTTPS 来源
ALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHS保持 false
TRUSTED_LOCAL_PATHS只列出确实允许读取的仓库根目录
REPOSITORY_STORAGE_PATH使用专用的持久目录，默认是 /var/lib/ershu/repositories

模型 API Key、仓库 Token 和 SSH 密钥由 Ershu 后台管理，不要写进前端环境变量。模型请求是否离开内网，取决于你创建的模型通道。

当前组合的程序版本和默认镜像来自发布目录，不需要复制到 /etc/ershu。如果公司使用内部镜像仓库，可以把基础设施镜像写进 /etc/ershu/image-overrides.env，把 LSP_IMAGES 写进 /etc/ershu/lsp-image-overrides.env。这些文件会在升级后继续生效，因此每次升级都要确认内部镜像已经同步了新版本。

修改配置后重启应用服务：

bash
sudo systemctl restart ershu.target
1

3. 管理 systemd 服务 ​

部署包提供这些服务：

服务用途默认状态
ershu-infrastructure.service启动并等待 PostgreSQL、Redis、Milvus、etcd 和 MinIO随应用启动
ershu-migrate.service在应用启动前升级数据库随应用启动
ershu-api.service网页和 HTTP API启用
ershu-worker.service执行仓库分析启用
ershu-mcp.service接收 MCP 客户端请求启用
ershu-poller.service定时检查仓库默认关闭
ershu.target一起启停 API、Worker 和 MCP启用

常用命令：

bash
sudo systemctl start ershu.target
sudo systemctl stop ershu.target
sudo systemctl restart ershu.target
sudo systemctl status ershu.target
journalctl -u ershu-api -u ershu-worker -u ershu-mcp -f
1
2
3
4
5

服务使用专用的 ershu 账号，默认只能写入 /var/lib/ershu，Worker 还可以写入 /var/cache/ershu。如果你把仓库放到其他目录，需要同步调整配置和 systemd 的写入权限。

API 与 MCP 可以通过 HTTP 检查。Worker 没有健康端口，需要查看启动日志，并确认真实任务能从 queued 进入分析。

4. 配置 HTTPS 和正式反向代理 ​

部署包里的 deploy/nginx/ershu-local.conf 只监听 127.0.0.1:8080，用于 SSH 隧道测试。生产环境应把其中的三条路由合并到你自己的 HTTPS 站点：

外部路径目标
/前端静态文件
/api/http://127.0.0.1:8000/api/
/mcp/http://127.0.0.1:8001/mcp/

/mcp/ 要保留末尾斜杠、Authorization 请求头和流式响应。代理还要传递真实 Host、客户端地址和外部 HTTPS 协议。前端与 API 使用同一域名，可以减少跨域 Cookie 配置错误。

上线前检查：

bash
curl -fsS https://ershu.example.com/api/v1/health
curl -fsS https://ershu.example.com/api/v1/health/dependencies
curl -fsS http://127.0.0.1:8001/health
1
2
3

MCP 的内部健康地址只说明进程还在运行。请再从外部客户端调用 get_server_info，检查 /mcp/ 的代理、认证和流式传输。

5. 备份和恢复 ​

默认数据目录是 /var/lib/ershu/infrastructure，其中包含 PostgreSQL、Redis、Milvus、etcd 和 MinIO 数据。仓库副本与分析工作区默认在 /var/lib/ershu/repositories。

生产备份至少覆盖：

  • PostgreSQL，其中保存账号、项目、权限、任务和文档；
  • Milvus、etcd 与 MinIO，或者准备好从仓库重建向量索引；
  • /etc/ershu 中的后端密钥和 OPAQUE 材料；
  • 仓库凭据、模型通道和依赖源使用的外部密钥系统；
  • 当前 versions.env 和反向代理配置。

Redis 主要保存短期限流和协调数据，不是业务记录来源。不要直接复制正在运行的数据库目录作为唯一备份。使用 PostgreSQL、Milvus 和对象存储支持的备份方式，并做一次恢复演练。

6. 单独评估 Worker 与 LSP ​

Worker 读取仓库，也可能访问私有依赖源。限制 GIT_ALLOWED_HOSTS 与 TRUSTED_LOCAL_PATHS，并让 REPOSITORY_STORAGE_PATH 指向专用目录。

LSP 默认关闭。启用后，Worker 会调用 Docker 启动短时语言服务容器。把 ershu 账号加入 Docker 组，等同于给它很高的宿主机权限。生产环境需要确认：

  • 镜像使用 versions.env 中的标签，需要更强固定时使用镜像摘要；
  • Docker 能看到与 Worker 相同的仓库绝对路径；
  • CPU、内存、进程数、会话数和超时符合主机容量；
  • 只启用项目实际使用的语言；
  • 依赖下载来源、缓存和 CA 证书经过审核。

权限要求更高时，请把 Worker 放到单独主机或受控的容器运行环境，不要直接开放宿主机 Docker。

7. 上线验收 ​

至少完成一次真实流程：

  1. 通过 HTTPS 创建管理员并登录。
  2. 测试语言模型和向量模型通道。
  3. 添加一个私有测试仓库并验证凭据。
  4. 运行完整项目分析，确认 Worker 推进任务。
  5. 打开 Wiki 引用，确认能回到正确仓库与提交。
  6. 分别检查关键词与语义搜索。
  7. 创建项目范围 MCP 密钥，从外部客户端调用 get_server_info 并读取一个项目。
  8. 重启 API、Worker 和 MCP，确认服务与任务状态能够恢复。
  9. 完成一次备份和恢复演练。

升级 ​

先下载并核对新的部署包，解压到新的版本目录。把下面的标签改成新版本，再执行：

bash
NEW_TAG=v1.0.1-20260813

sudo systemctl stop ershu.target

cd "/opt/ershu/releases/${NEW_TAG}"
sudo bash deploy/systemd/install.sh --uv-bin "$(command -v uv)"

sudo systemctl start ershu.target

安装脚本会安装新组合指定的 ershu[all]，停掉旧基础设施，更新 systemd 文件，并切换 /opt/ershu/current。它只会更新 /etc/ershu/.env 中的组合版本，已有密钥和部署设置会保留。启动前，请对照新发布包中的示例检查是否增加了配置项。

确认后端健康、登录、任务、Wiki、搜索和 MCP 都正常后，再切换 /opt/ershu/frontend/current。保留旧发布目录，直到验收结束。

数据库升级后，切回旧 Python 包不一定能完成回退。升级前先确认数据库兼容范围和恢复方案。
