On this page

Start Ershu and reach the sign-in page ​

This page is for maintainers who already have access to the internal component sources. The goal is to start the infrastructure, API, Worker, and frontend so that you can continue in the web interface.

Public package installation is not available yet

The bundle and backend modules still obtain Core and other dependencies from private development sources. Without the required Git and SSH access, uv sync --all-extras --frozen fails while fetching those dependencies. There is currently no verified public installation command to use instead.

The commands below come from the current repository manifests and READMEs. They describe the intended procedure; they do not claim to have succeeded on your machine.

Prerequisites ​

Before starting, make sure you have:

  • Python 3.14;
  • UV;
  • Docker and Docker Compose;
  • Node.js 24;
  • access to the current private component sources; and
  • a separate checkout of the matching frontend repository.

Core is a shared package and does not run as a separate process. The first web analysis requires the PostgreSQL and Milvus infrastructure, the API, the Worker, and the frontend. Start MCP and the repository poller only when you need those features.

Step 1: Start the infrastructure ​

In the ershu bundle repository, copy the Compose settings:

bash
cp .env.compose.example .env.compose
1

Open .env.compose, replace the example PostgreSQL and MinIO passwords, and start the services:

bash
docker compose --env-file .env.compose up -d
docker compose --env-file .env.compose ps
1
2

The ps output should show PostgreSQL, Redis, Milvus, etcd, and MinIO running. If a service repeatedly restarts, inspect that container before attempting a database migration.

Step 2: Prepare backend settings ​

Copy the current settings template:

bash
cp .env.example .env
1

Replace the example passwords and keys as directed by the comments. Confirm that the database, Redis, and Milvus addresses point to the services from the previous step. Do not put model names, model API keys, or model endpoints in .env; those belong to model channels in the web administration area.

At the end of this step, you should have a local-only .env without example secrets that might accidentally reach a real environment.

Step 3: Install the backend and run migrations ​

Run these commands only if your account can access the private component sources:

bash
uv sync --all-extras --frozen
uv run ershu-db upgrade head
1
2

Both commands should finish with exit code 0. If the first command cannot fetch Core or another Ershu package, you have reached the current public-installation limitation. Do not work around it by deleting the lockfile or substituting an unverified package.

Step 4: Start the API and Worker ​

Open two terminals and leave both processes running.

Terminal A:

bash
uv run ershu-api
1

Terminal B:

bash
uv run ershu-worker
1

Open http://127.0.0.1:8000/health. A live API returns a response whose status is ok. This endpoint only confirms that the API process is alive. /api/v1/health/dependencies also checks the database and Milvus, but it does not check Redis.

The Worker does not currently expose a browser health endpoint. Its process should remain running instead of exiting immediately. The final proof is that the first queued run advances through its analysis stages.

Start MCP in another terminal if you need it:

bash
uv run ershu-mcp
1

Start the repository poller separately if you want scheduled repository checks:

bash
uv run ershu-api-poller
1

Neither process is required for the first analysis through the web interface.

Step 5: Start the frontend ​

In the separate frontend repository, run:

bash
cp .env.example .env.local
npm ci
npm run dev
1
2
3

The development server uses http://localhost:3000 by default and proxies /api to http://localhost:8000. If the API runs elsewhere, change VITE_DEV_API_PROXY in .env.local and restart the development server.

Open http://localhost:3000:

  • a new database redirects you to initial administrator setup;
  • a database that already contains users redirects you to sign-in; and
  • repeated network errors mean that the frontend still cannot reach the API.

You are now ready to create your first project.
