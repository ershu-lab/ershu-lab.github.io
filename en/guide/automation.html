Track repository updates automatically ​

Ershu can check repository commits in two ways: a separate Poller fetches repositories on a UTC cron schedule, or an external system calls a signed webhook. Both paths first determine whether a commit is already analyzed or queued. They create fact-refresh work only when the commit still needs processing.

Automatic triggers update the repository tree, code index, knowledge graph, and search index. They do not regenerate AI documents. Start a document-capable analysis separately when documents must follow the new commit.

Choose a trigger ​

MethodBest fitAdditional dependencySuccess signal
Scheduled pollingThe repository host cannot notify Ershu, or Ershu should control the check intervalA continuously running ershu-api-poller and RedisA Poller audit record appears and the result is queued or an explained skipped
Signed webhookThe external system can send a custom HTTP request when a commit changesA sender that can calculate Ershu's HMAC formatThe webhook returns HTTP 202 with queued or an explained skipped
Manual pollYou want to validate repository access and change detection immediatelyAn authenticated user with project-management permissionThe manual poll returns HTTP 202 with an interpretable result

In every case, the Worker claims the actual work from the PostgreSQL queue. When no Worker is running, queued means only that the request reached the queue.

Configure scheduled polling ​

In repository trigger settings, set poll_cron before enabling poll_enabled. The schedule must be a valid five-field cron expression and is always interpreted in UTC. For example, 0 * * * * checks at the start of every UTC hour.

The corresponding management route is:

text
PATCH /api/v1/projects/{project_id}/repositories/{repository_id}/triggers
1

Because this request uses an authenticated session and CSRF protection, the web settings page is normally the safer interface. The API rejects an enabled poller without a schedule.

Run the Poller as a separate process. This is a recommended command; it has not been run in your environment:

bash
uv run ershu-api-poller
1

By default, the process scans every 30 seconds and considers at most 100 due repositories per batch. It holds a renewable Redis lease for 120 seconds by default, so only the instance that owns the lease performs a scan. See the environment reference for the supported ranges.

For one diagnostic cycle, the recommended command is:

bash
uv run ershu-api-poller --once
1

Exit code 0 only means that the cycle had no unhandled process error. Inspect the repository's last-poll time, audit records, and new run state to learn whether it found a change.

Configure a signed webhook ​

In repository trigger settings, save a webhook_secret of at least 16 characters before enabling webhook_enabled. Later reads expose only has_webhook_secret; they never return the original secret.

The webhook endpoint is:

text
POST /api/v1/webhooks/repositories/{repository_id}
1

The JSON body may contain:

FieldConstraintPurpose
branchOptionalRecords the target branch
commit_shaOptional; exactly 40 or 64 hexadecimal charactersSelects the exact commit to refresh
eventOptional; at most 64 charactersDescribes the trigger in the result and audit record

The sender must keep the exact request-body bytes and construct three headers:

HeaderContent
X-Ershu-Webhook-TimestampCurrent Unix time; the server permits at most 300 seconds of skew from the database clock
X-Ershu-Webhook-NonceA value unique to this delivery; at most 255 characters, with no colon or line break
X-Ershu-Webhook-SignatureLowercase hexadecimal HMAC-SHA256 digest of the message below

Build the signed message from exact bytes:

text
UTF-8(timestamp) + NUL + UTF-8(nonce) + NUL + raw_request_body
1

Use the repository's stored webhook_secret as the HMAC key. The signature covers the final transmitted bytes. Reformatting JSON after signing causes authentication to fail. Reusing the same nonce inside the replay-protection window is rejected as well.

This body shows only the request shape. It has no usable signature and cannot be sent unchanged:

json
{
  "branch": "main",
  "commit_sha": "<40-or-64-character-commit>",
  "event": "push"
}

Interpret the trigger response ​

An authenticated, valid webhook or manual poll returns HTTP 202. The response status determines what happened:

statusCommon reasonMeaning
queuedwebhook, poll_detected_change, or the sender's eventFact-refresh work was created or reused for the Worker
skippedcommit_already_analyzedFacts for this branch and commit are already current
skippedcommit_already_queuedWork for the same repository, branch, and commit is already queued
skippedlocal_workspace_dirtyA local workspace has uncommitted changes and is not treated as a reproducible commit
skippedrepository_has_no_git_commitNo Git commit can be identified for the workspace

A queued response includes a run_id. Observe it in the run page or with MCP get_run_status. The automatic refresh is complete only after the run reaches a completed state and the repository tree, code, graph, and search states have updated.

Validate the full loop before relying on it ​

These are recommended checks; they have not been performed for your deployment:

  1. Save the trigger settings, read them back, and confirm the enabled flags, cron rule, and has_webhook_secret.
  2. Manually poll a known commit or send one correctly signed test webhook.
  3. Confirm an HTTP result of queued, or a skipped reason that matches the expected state.
  4. For queued, confirm that the Worker claims the returned run_id.
  5. Wait for completion, then inspect the repository commit and freshness of each fact layer.
  6. Send the same commit again and confirm commit_already_analyzed or commit_already_queued instead of endless duplicate runs.

If a schedule never fires, first confirm that ershu-api-poller is running separately, then inspect Redis, the UTC cron rule, and repository credentials. The API web process does not execute schedules itself.
