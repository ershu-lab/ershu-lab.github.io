On this page

User guide ​

You do not need to read every setting before trying Ershu. Start with the path that matches the job in front of you.

I want to get it running ​

  1. Deploy Ershu quickly on a Linux server
  2. Create the first project
  3. Start and follow the first analysis

This path downloads a deployment archive, installs the backend from PyPI, starts services with systemd, and serves the prebuilt frontend. The server does not need source repositories or Node.js.

I am preparing a long-running deployment ​

Complete the one-machine check first, then read move the quick deployment into production. It covers HTTPS, production settings, backups, Worker privileges, and upgrade order.

I already have results and want to use them ​

  • Read the wiki, search the project, and ask questions
  • Debug analysis, retrieval, and relationship data

Docs is best for understanding a topic, Search for locating an implementation, and project chat for combining several sources. Whichever route you use, exact conclusions should lead back to current source.

I want coding agents to read the project ​

Follow Connect an MCP client. Create a project-scoped key, then verify server identity, project discovery, wiki access, search, and source reading in stages. MCP is read-only and does not modify repositories for the client.

I want project facts to follow repository updates ​

Read Track repository updates. Scheduled polling and signed webhooks detect commits and create refresh runs. The Worker still performs the actual work.

Three boundaries that prevent common mistakes ​

  • A live process does not mean the whole system is ready. API health does not check Worker, Redis, or model channels.
  • A queued run is not a completed run. Without a Worker, it remains in queued.
  • A fact refresh does not rewrite the wiki. Automated refresh updates trees, code indexes, search indexes, and knowledge relationships. A document-producing analysis is still needed for new prose.
