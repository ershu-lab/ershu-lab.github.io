Start and follow your first analysis ​

Repository analysis is a background job. The API creates a run, the Worker takes it from the queue, and the frontend displays its current snapshot and later events. This page explains how to tell whether work is advancing and what to inspect at the end.

Check before starting ​

Before the first run, make sure that:

  • the project has at least one active repository;
  • an enabled large language model (LLM) channel is available;
  • the API and Worker use the same database settings;
  • the Worker process is running; and
  • any private remote repository has a usable credential.

If the Worker is not running, the API may still create the run, but it will remain in the queue.

Step 1: Use full-project scope ​

Open the project's Runs page and choose New run.

For the first run, use:

  • type: Full project (full_project);
  • repository scope: all active repositories;
  • branch: leave empty for repository defaults, or enter a branch you know exists;
  • LLM channel: keep the project default or select another enabled channel;
  • embedding channel: select a separate enabled channel when you need a semantic index; and
  • parallel processing: leave disabled when unsure, which uses a repository parallelism of 1.

Until a baseline exists, the backend permits only a full-project run and requires every active repository. The frontend shows a baseline notice and locks the repository scope.

Choose New run. The record appears at the top of the list. Any of queued, running, scanning, analyzing, or finalizing means that the run is still active.

Step 2: Confirm that the Worker advances the run ​

While any run is active, the list refreshes about every five seconds. Open the run detail to see the persisted snapshot, timeline, analysis blocks, tool calls, and usage that are available at its current stage.

If the run remains queued for a long time:

  1. Run systemctl status ershu-worker and confirm that the Worker service is running. For a source installation, check the terminal that started Worker.
  2. Confirm that the Worker and API read the same database and related key settings.
  3. Read the current error with journalctl -u ershu-worker -n 200 --no-pager instead of creating repeated runs.

A useful intermediate result is a transition from queued into scanning, analysis, or finalization, together with new timeline content on the detail page.

Step 3: Refresh without losing progress ​

When an active run is opened, the frontend first loads its current snapshot and then receives events after the snapshot cursor. You can refresh the browser or return to the same run later without replaying its earliest output.

After a successful refresh, you should see:

  • the same run identifier;
  • the analysis content already persisted; and
  • new events continuing after the current cursor, without a second run being created.

The browser event stream is not the job itself. Closing the page does not cancel the Worker run.

Step 4: Decide whether the run is complete ​

Terminal states are:

  • completed: the run completed;
  • completed_with_warnings: the run completed with warnings to inspect;
  • failed: the run failed; and
  • cancelled: the run was cancelled.

For a completed run, including one with warnings, the frontend loads the final result directly and does not keep an event-stream connection open. The detail page can show the final process text, analysis blocks, usage, warnings, and documents produced by that run.

Verify that:

  1. The state is completed or completed_with_warnings.
  2. The detail page shows a final result instead of waiting for more events.
  3. The document area lists the documents that were actually produced.
  4. The search-index status matches your expectation. If it is degraded or unavailable, read the warning instead of treating it as a complete semantic index.

completed_with_warnings is not an unconditional success. You can use the results that exist, but first identify any repository, document, or index that did not complete.

Cancel and retry ​

A user with project management access can cancel an active run. After the request completes, the state becomes cancelled. Closing the page alone never cancels it.

The retry action on a terminal run creates a new run record. Follow the new record; the old one does not return to an active state.

Once documents exist, continue with reading documents, searching the project, and asking questions.
