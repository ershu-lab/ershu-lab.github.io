Move the quick deployment into production ​

The quick deployment already uses release archives, PyPI, and systemd. Production keeps the same directories and services. You do not need to replace them with source installations. Before launch, add a domain and TLS, production settings, backups, monitoring, and access controls.

Recommended shape ​

API, MCP, and Worker may start on one trusted host or run separately. They must use the same PostgreSQL database. When vector retrieval is enabled, they must also use the same Milvus database.

The systemd files in the deployment archive target one host. For a split deployment, create equivalent services on each host while keeping the same account, configuration, and storage boundaries.

1. Install only published releases ​

Keep every composition in its own directory:

text
/opt/ershu/releases/<tag>
1

Verify the archive against SHA256SUMS from the same GitHub Release, then run its installer:

bash
sudo bash deploy/systemd/install.sh --uv-bin "$(command -v uv)"
1

The installer reads the composition version from versions.env and installs the exact ershu[all] release from PyPI. Components may use different versions in later compositions. Operators still install the ershu version selected by the composition.

/opt/ershu/current points to the active release. Configuration and data live outside the version directory, so switching releases does not overwrite secrets, databases, or repository caches.

2. Use production settings ​

Backend settings live in /etc/ershu/.env. Infrastructure settings live in /etc/ershu/compose.env. Review at least these values:

SettingProduction requirement
ENVIRONMENTSet to production
HOST, MCP_HOSTUsually keep 127.0.0.1 and expose only the reverse proxy
SESSION_COOKIE_SECURESet to true
CORS_ORIGINSList only the real HTTPS frontend origin
PROXY_HEADERSSet to true behind a reverse proxy
FORWARDED_ALLOW_IPSTrust only the real proxy addresses
OPAQUE_SERVER_SETUPKeep the value generated during the first deployment; do not regenerate it during upgrades
SECRET_KEY, ENCRYPTION_KEY, MCP_KEY_PEPPERStore three different random values in a secret manager
MCP_BUILD_COMMITSet the complete 40-character commit for the deployed MCP release
MCP_ALLOWED_HOSTS, MCP_ALLOWED_ORIGINSAllow only the real domain and HTTPS origin
ALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHSKeep false
TRUSTED_LOCAL_PATHSList only repository roots that Ershu may read
REPOSITORY_STORAGE_PATHUse dedicated persistent storage, by default /var/lib/ershu/repositories

Model API keys, repository tokens, and SSH keys belong in Ershu administration, not frontend environment variables. Whether model traffic leaves the private network depends on the model channels you create.

The active release supplies the composition version and default images, so they do not need to be copied into /etc/ershu. If your company uses an internal registry, put infrastructure image replacements in /etc/ershu/image-overrides.env and put LSP_IMAGES in /etc/ershu/lsp-image-overrides.env. These files remain active after an upgrade. Check that the internal registry has the new images before switching releases.

Restart the application services after a configuration change:

bash
sudo systemctl restart ershu.target
1

The units use a dedicated ershu account. They can write to /var/lib/ershu; Worker can also write to /var/cache/ershu. If repositories live elsewhere, update both the Ershu setting and the systemd write permissions.

API and MCP have HTTP health checks. Worker has no health port. Check its startup log and confirm that a real task moves out of queued.

4. Add HTTPS and a production reverse proxy ​

deploy/nginx/ershu-local.conf listens only on 127.0.0.1:8080 and is intended for an SSH-tunnel evaluation. Copy its three routes into your own HTTPS site for production:

External pathTarget
/Frontend static files
/api/http://127.0.0.1:8000/api/
/mcp/http://127.0.0.1:8001/mcp/

The /mcp/ route must retain its trailing slash, the Authorization header, and streaming responses. Pass the real Host, client address, and external HTTPS scheme to the backend. Serving the frontend and API from one domain avoids many cross-origin cookie mistakes.

Check the public domain before launch:

bash
curl -fsS https://ershu.example.com/api/v1/health
curl -fsS https://ershu.example.com/api/v1/health/dependencies
curl -fsS http://127.0.0.1:8001/health
1
2
3

The internal MCP health check only shows that its process is running. Call get_server_info through the public /mcp/ route to test proxying, authentication, and streaming.

5. Back up and restore ​

The default data directory is /var/lib/ershu/infrastructure, which contains PostgreSQL, Redis, Milvus, etcd, and MinIO data. Repository copies and analysis workspaces default to /var/lib/ershu/repositories.

A production backup should cover:

  • PostgreSQL, which stores users, projects, permissions, runs, and documents;
  • Milvus, etcd, and MinIO, unless rebuilding vector indexes from repositories is an accepted recovery plan;
  • backend secrets and OPAQUE material from /etc/ershu;
  • external secret systems used by repository credentials, model channels, and dependency sources;
  • the active versions.env and reverse-proxy configuration.

Redis mainly holds short-lived throttling and coordination data. It is not the source of business records. Do not rely on copying live database directories. Use backup methods supported by PostgreSQL, Milvus, and the object store, then perform a restore test.

6. Review Worker and LSP separately ​

Worker reads repositories and may access private dependency sources. Restrict GIT_ALLOWED_HOSTS and TRUSTED_LOCAL_PATHS, and keep REPOSITORY_STORAGE_PATH in a dedicated directory.

LSP is disabled by default. When enabled, Worker invokes Docker to run short-lived language servers. Adding the ershu account to the Docker group gives it substantial host privileges. Confirm that:

  • image tags come from versions.env, with image digests used where stronger pinning is required;
  • Docker can see the same absolute repository paths as Worker;
  • CPU, memory, process, session, and timeout limits fit the host;
  • only languages used by the project are enabled;
  • dependency sources, caches, and CA bundles have been reviewed.

Use a separate Worker host or a controlled container runtime when the host Docker socket grants too much access.

7. Production acceptance check ​

Complete a real workflow before launch:

  1. Create an administrator and sign in over HTTPS.
  2. Test the language-model and embedding channels.
  3. Add a private test repository and verify its credential.
  4. Run a full-project analysis and confirm that Worker advances the task.
  5. Open a Wiki citation and confirm its repository and commit.
  6. Check keyword and semantic search separately.
  7. Create a project-scoped MCP key, call get_server_info from an external client, and read one project.
  8. Restart API, Worker, and MCP, then confirm that services and task state recover.
  9. Complete a backup and restore exercise.

Upgrade ​

Download and verify the new deployment archive, then extract it to a new release directory. Replace the tag below with the new release and run:

bash
NEW_TAG=v1.0.1-20260813

sudo systemctl stop ershu.target

cd "/opt/ershu/releases/${NEW_TAG}"
sudo bash deploy/systemd/install.sh --uv-bin "$(command -v uv)"

sudo systemctl start ershu.target

The installer installs the new composition's ershu[all], stops the old infrastructure, updates the systemd units, and switches /opt/ershu/current. It updates only the composition version in /etc/ershu/.env, leaving existing secrets and deployment settings in place. Compare the new configuration examples with the active files before starting the services.

After health, sign-in, tasks, Wiki, search, and MCP all pass, switch /opt/ershu/frontend/current. Keep the previous release directory until acceptance is complete.

A database migration may prevent a package-only rollback. Confirm database compatibility and recovery procedures before upgrading.
