Permissions and security: define every trust boundary ​

Ershu handles source repositories, login state, and model credentials. Secure deployment is not a single switch. Define the trust boundary for browsers, repositories, webhooks, MCP, and administrator actions separately.

Protect four kinds of server material ​

SettingPurposeEffect of rotation
SECRET_KEYSigns access and CSRF tokensExisting access and CSRF tokens become invalid
ENCRYPTION_KEYEncrypts model keys, repository credentials, and login material stored in the databaseExisting ciphertext may become unreadable
MCP_KEY_PEPPERAdds server-side material outside the database to MCP key digestsEvery existing MCP key becomes invalid
OPAQUE_SERVER_SETUPMaintains the server identity for password registration and loginExisting password records may no longer authenticate

The first three values must be distinct, at least 32 characters long, and different from the weak values listed in source. Inject them through the deployment platform's secret manager; never store them in a repository, image, or public log.

In development, the API can create OPAQUE_SERVER_SETUP during its first startup and store it encrypted in the database. Production requires an explicit, stable value. Current startup validation checks its presence and basic strength; actual authentication must also decode it as valid OPAQUE server material. An arbitrary long string is not sufficient.

Protect browser sessions ​

A production environment needs at least:

dotenv
ENVIRONMENT=production
SESSION_COOKIE_SECURE=true
SESSION_COOKIE_SAMESITE=lax
CORS_ORIGINS=["https://ershu.example.org"]
1
2
3
4

Replace the example domain with the real frontend origin. Browser protection has three layers:

  1. In production, requests under /api/ and /mcp must appear as HTTPS or receive a 400 response.
  2. A write request authenticated by session Cookie must include both a valid X-Ershu-CSRF header and CSRF Cookie. When the request has Origin or Referer, that origin must also be the current site or an entry in CORS_ORIGINS; otherwise the API returns 403.
  3. A request with Authorization: Bearer ... does not authenticate through browser Cookies, so it bypasses the CSRF check but still passes through token authentication and endpoint authorization.

SESSION_COOKIE_SAMESITE=none is normally appropriate only when a deployment intentionally needs cross-site Cookies. It still requires secure Cookies and a precise origin list. Do not use broad origins to hide a proxy or domain error.

If a reverse proxy terminates HTTPS, put only the actual proxy addresses in FORWARDED_ALLOW_IPS. The API decides whether a request is secure from its scheme; untrusted forwarded headers or a missing forwarded scheme can cause incorrect acceptance or rejection.

Restrict remote Git URLs ​

By default, repository URLs may use only:

  • https://;
  • ssh://;
  • SCP-like SSH syntax such as user@host:path.

http:// and git:// require ALLOW_INSECURE_GIT_URLS=true. file:// requires ALLOW_FILE_GIT_URLS=true. Both switches default to false and should remain false in production unless the risk has been explicitly evaluated and isolated.

GIT_ALLOWED_HOSTS defines the remote host boundary:

  • with an empty list, the host must still resolve, and loopback, private, link-local, multicast, reserved, and unspecified addresses are rejected by default;
  • with a non-empty list, a host that does not match is rejected immediately;
  • an exact or wildcard allowlist match may resolve to a private address, but loopback, link-local, and the other blocked classes remain rejected;
  • *.example.org matches subdomains but not example.org itself.

List the actual Git hosts in production and avoid *. Host validation runs before later clones and fetches; changing the list does not reinspect cache content that already exists.

Restrict local repository paths ​

Core trusts a local repository workspace only when at least one condition is true:

  • it is inside the cache managed by REPOSITORY_STORAGE_PATH;
  • it is the same as, or below, an entry in TRUSTED_LOCAL_PATHS;
  • the directory itself contains .git.

ALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHS=true is a development fallback. It applies only when there is no trusted-path list and the environment is not production. Production validation rejects it. Administrators should still add only the paths that need analysis: “trusted” means readable, not intrinsically safe.

Assign repository credentials ​

A repository can use a dedicated token, an SSH private key, or a credential that names a process environment variable. Core prefers the repository-specific credential. Only when there is no dedicated token does a GitHub or GitLab repository fall back to global GITHUB_TOKEN or GITLAB_TOKEN.

Tokens are exposed only to an individual Git subprocess, and temporary credential files are removed after the command. Database-stored tokens and SSH keys depend on ENCRYPTION_KEY for decryption. Still grant the minimum permission required: repository read access, without write or organization-management permission.

Sign repository webhooks correctly ​

Before enabling a webhook, a project manager must set a secret with at least 16 characters. Every request uses three headers:

  • X-Ershu-Webhook-Timestamp: no more than five minutes away from server time;
  • X-Ershu-Webhook-Nonce: single-use, at most 255 characters, with no colon or newline;
  • X-Ershu-Webhook-Signature: the hexadecimal HMAC-SHA256 digest made with the webhook secret.

Build the signed bytes in this exact order: timestamp, one NUL byte, nonce, one NUL byte, and the unchanged raw request body. An older body-only signature will fail. The API stores used nonces in the database and rejects reuse inside the validity window.

Tighten the MCP network boundary ​

In production, MCP also checks that:

  • MCP_BUILD_COMMIT is the exact 40-character hexadecimal source commit;
  • the process can read installed ershu-mcp package metadata;
  • MCP_ENABLE_DNS_REBINDING_PROTECTION=true;
  • neither MCP_ALLOWED_HOSTS nor MCP_ALLOWED_ORIGINS is empty.

These settings protect the network entry point. Project and tool permissions still come from the MCP key scope, user identity, and project membership. An allowed network origin is not a substitute for endpoint authorization.

Verifiable production checklist ​

  • Use four independent, stable pieces of server material, and confirm in a backup-recovery exercise that old ciphertext remains decryptable.
  • Request a protected API over HTTPS. The HTTP request should be rejected, while the HTTPS response should include HSTS.
  • Sign in from an allowed frontend origin and complete one write. Remove the CSRF header and confirm that the same write returns 403.
  • Add or refresh a repository whose host is outside GIT_ALLOWED_HOSTS; it should be rejected before Git runs.
  • Send the same webhook timestamp, nonce, body, and signature twice; the second request should be rejected.
  • Call the administrator system-settings endpoint as a regular user and expect 403; only an administrator should read it.
  • Before rotating MCP_KEY_PEPPER, plan to issue replacement MCP keys because old keys will stop working.

These are acceptance conditions, not a claim that this page has executed the tests in your environment.
