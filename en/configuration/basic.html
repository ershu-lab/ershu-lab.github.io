Basic configuration: start the service safely ​

This page answers one question: in an existing Ershu development workspace, or an environment where the modules are already installed, what is the minimum configuration the API needs to start safely?

The backend still pins Core to a private Git source. This page therefore does not claim that a fresh installation can currently be completed using public packages alone.

Prepare three external services ​

ServiceHow the API uses itSettings
PostgreSQLStores accounts, projects, runs, documents, and system settings; the API reads it during startupDATABASE_URL
RedisStores failed-login counters for login rate limitingREDIS_URL
MilvusStores and queries vector indexes; the dependency health route connects to itMILVUS_URI, MILVUS_TOKEN, MILVUS_DB_NAME

The database is part of API startup. Redis is connected when login rate limiting is first used. Milvus is used by retrieval and the dependency check. A running process does not prove that all three services are available.

Write a minimal development configuration ​

API and Core use Pydantic Settings to read process environment variables and a file named .env. The following example is suitable for local development. Every value in angle brackets must be replaced rather than copied literally.

dotenv
ENVIRONMENT=development
LOG_LEVEL=INFO

DATABASE_URL=postgresql+asyncpg://ershu:<database-password>@localhost:5432/ershu
REDIS_URL=redis://localhost:6379/0
MILVUS_URI=http://localhost:19530
MILVUS_TOKEN=
MILVUS_DB_NAME=default

SECRET_KEY=<independent-random-value-at-least-32-characters>
ENCRYPTION_KEY=<different-random-value-at-least-32-characters>

Generate the three server-side secrets independently. Each must contain at least 32 characters, and weak values such as change-me and replace-me are rejected. In an existing API development environment, the following command generates one random value. Run it three times and assign each result to a different setting.

bash
uv run python -c "import secrets; print(secrets.token_urlsafe(48))"
1

The command only prints text; it does not update .env. Never commit the generated values to Git.

Understand why these values matter ​

SettingPurposeDirect result of a bad value
SECRET_KEYSigns access and CSRF tokensAPI creation rejects a weak value; rotating it invalidates existing login state
ENCRYPTION_KEYEncrypts sensitive values stored in the databaseAPI creation rejects a weak value; rotating it can make old ciphertext unreadable
MCP_KEY_PEPPERKeys the server-side digest for MCP keysAPI creation rejects a weak value; rotating it invalidates all existing MCP keys
DATABASE_URLSelects the shared relational databaseThe API lifespan cannot complete its startup database read
CORS_ORIGINSLists browser origins allowed to send credentialed API requestsBrowser requests from a different origin are blocked
REPOSITORY_STORAGE_PATHHolds remote repository cachesLater clone, fetch, and cache maintenance operations use the wrong location

OPAQUE_SERVER_SETUP is long-lived server material for the password login protocol. When it is empty in development, the API creates material in the database and encrypts it with ENCRYPTION_KEY. Production rejects an empty or weak value and requires stable, correctly encoded material. The current source does not expose a project command that generates it, so a deployment process must generate and protect it separately; do not rely on the nonexistent function named by an older example.

Tighten four settings in production ​

When ENVIRONMENT is prod or production, source validation also enforces:

  • SESSION_COOKIE_SECURE=true;
  • SESSION_COOKIE_SAMESITE is one of lax, strict, or none;
  • OPAQUE_SERVER_SETUP is present and passes the strength check;
  • ALLOW_DEV_OPEN_LOCAL_REPOSITORY_PATHS=false.

Production requests under /api/ and /mcp must also use HTTPS. If a reverse proxy terminates TLS, check PROXY_HEADERS and FORWARDED_ALLOW_IPS and trust only the real proxy addresses.

Verify the configuration before and after startup ​

In an API repository where dependencies are already installed, upgrade the database and start the service:

bash
uv run ershu-db upgrade head
uv run ershu-api
1
2

These are project entry points, not a claim that they have succeeded in your environment. A correct setup should meet each of these conditions:

  1. The API no longer reports weak server secrets, insecure production cookies, or a production-only local-path escape hatch.
  2. GET http://127.0.0.1:8000/health returns {"status":"ok"}.
  3. In GET http://127.0.0.1:8000/api/v1/health/dependencies, the top-level status is ok, while both database.ok and milvus.ok are true.
  4. If step 2 succeeds but step 3 reports degraded, only the API process is alive. Fix the database or Milvus before treating the deployment as ready.

The dependency route does not check Redis. To verify the full login path, complete a real login attempt as well. If Redis is unavailable, login rate limiting reports a service-unavailable error.

Source locations ​

  • core/src/ershu/core/config.py: shared settings, defaults, secret checks, and production validation.
  • api/src/ershu/api/runtime_settings.py: API settings, ranges, and production validation.
  • api/src/ershu/api_main.py: startup, HTTPS, CORS, CSRF, and the liveness route.
  • api/src/ershu/api/routes/health.py: database and Milvus dependency response.
  • api/src/ershu/api/services/auth/login_limits.py: Redis-backed login rate limiting.
  • api/.env.example: current environment-variable inventory; its old OPAQUE_SERVER_SETUP generation function does not exist and must not be copied.
  • api/pyproject.toml: the ershu-api command and the currently pinned private Core source.
