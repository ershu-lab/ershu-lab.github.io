Development troubleshooting ​

When troubleshooting Ershu, first identify the layer where progress stops: dependency installation, infrastructure, API, Worker, frontend, or the output of one run. A successful liveness check does not prove that the complete analysis path works.

uv sync cannot fetch an Ershu package ​

Typical symptom: Installation reports that an Ershu component version is missing, uv.lock is absent, or the Python package index cannot be reached.

Common cause: The directory is not from a published tag, component publishing is still in progress, the lock file changed, or the network proxy cannot reach the package index.

Action:

  1. Confirm that the deployment directory came from a published tag or Release archive.
  2. Confirm that uv.lock exists and has no local changes.
  3. Check whether the component version in the error is available from the configured index.
  4. Check the proxy, certificate, and package-index settings used by UV.

Recovery evidence: uv sync --locked --extra all finishes without rewriting the lock file. Skipping one component is not a successful composition install.

Frontend dependency installation or startup fails ​

Check the version first:

bash
node --version
npm ci
1
2

The frontend is fixed to Node.js 24. The version should start with v24, and npm ci should exit with code 0. Do not hide a version mismatch by updating the lockfile.

If npm run dev starts but the page is blank, inspect both the browser console and the build error in the terminal. After correction, http://localhost:3000 should enter setup, sign-in, or a project page.

The frontend reports a network error or keeps loading ​

Check the API directly:

text
http://127.0.0.1:8000/health
1
  • No connection means the API is not running, uses another port, or is blocked by a local network rule.
  • A response with status ok means the API process is alive; continue with the frontend proxy.

In development, the frontend proxies /api to http://localhost:8000 by default. If the API runs elsewhere, change VITE_DEV_API_PROXY in .env.local and restart npm run dev.

Recovery evidence: The frontend root enters initial administrator setup, sign-in, or the project list according to database state and no longer reports repeated request failures.

/health works but project operations fail ​

/health and /api/v1/health only report API liveness. Use the dependency endpoint for a wider check:

text
http://127.0.0.1:8000/api/v1/health/dependencies
1

This response checks the database and Milvus and reports ok or degraded. It does not check Redis. An ok response therefore does not prove that login rate limiting, queue-related connections, or the Worker are healthy.

Action: Use the database and milvus fields to check addresses, credentials, and service state. Inspect Redis and the Worker separately.

A run remains queued ​

Most likely cause: The Worker is not running, or the Worker and API connect to different databases.

Check in order:

  1. Confirm that uv run ershu-worker is still running.
  2. Confirm that the API and Worker use the same database, Redis, Milvus, and related key settings.
  3. Inspect the current Worker error, especially repository credentials, branch selection, and model channels.
  4. Correct the cause before deciding to cancel or retry. Do not create repeated identical runs.

Recovery evidence: The run moves from queued to scanning, analyzing, or finalizing, and the detail page gains new timeline content.

The first run does not allow repository or incremental scope ​

This is an expected restriction, not a frontend failure. A project must first establish a full-project baseline that covers every active repository.

Select Full project (full_project) and keep all active repositories in scope. After the baseline completes, the capability response may enable repository or incremental runs. Always use the options returned for the current project.

Recovery evidence: The first full-project run can be submitted and appears in the run list.

A run fails because of model configuration ​

Repository analysis requires a usable LLM channel. Model names, API keys, and endpoints do not come from .env.

On the administrator model channels page, confirm that:

  • at least one llm channel is enabled;
  • its connection or model test works;
  • the project or run selects a valid channel; and
  • HTTPS is used when submitting a secret through a non-localhost name.

Recovery evidence: A new run no longer fails immediately for lack of an LLM channel and advances into scanning or analysis.

Semantic search is unavailable or hybrid search is degraded ​

Inspect search_index_status on the latest run:

  • indexed means the semantic index was built;
  • degraded means part of the capability is unavailable and its warning needs attention; and
  • unavailable means there is no usable semantic index.

Semantic mode does not silently pretend to be keyword search. Hybrid mode can explicitly fall back to keyword results and shows a degradation notice.

Action: Confirm that a separate enabled embedding channel exists, that the run selected it, and that the run warnings and Milvus dependency state are clear.

Recovery evidence: After a new full analysis builds the index, a semantic query returns results without an unresolved degradation reason.

Docs is empty or chat has no context ​

Check in order:

  1. Is the latest run completed or completed_with_warnings?
  2. Does the run detail actually list generated documents?
  3. For a run with warnings, did a repository or document stage fail?
  4. Is chat open in the intended project?
  5. Does the project have a usable model channel and searchable content?

Chat on Docs is always project-scoped. It does not automatically narrow itself to the current document or section, so citations from another repository are not necessarily a scope error.

Recovery evidence: Docs opens a generated document, and citations in a chat answer open the corresponding source preview.

Authenticated writes are rejected by CSRF or transport policy ​

For local development, prefer localhost or 127.0.0.1. Production and any other hostname require HTTPS.

When HTTPS terminates at a reverse proxy, check that:

  • the external Host and Origin are preserved;
  • X-Forwarded-Proto contains the real external scheme;
  • the API trusts the actual proxy source; and
  • cookie and allowed-origin settings match the external address.

Do not disable CSRF or secure cookies to make a request pass.

Recovery evidence: Sign-in restores a session, and cookie-authenticated writes such as project creation or model-channel changes are no longer classified as cross-site or insecure.

An MCP client connects to the wrong port ​

In a same-origin deployment, /api/ must reach the API on port 8000, while /mcp/ must reach MCP on port 8001. Do not send /mcp/ to the API or accidentally remove the MCP path prefix in the proxy.

Recovery evidence: The web API remains usable, and the MCP client can establish its separate connection through /mcp/.

A completed run no longer receives live events ​

This is expected. An active run uses a snapshot and events after its cursor. completed and completed_with_warnings load the final result directly and no longer connect to the event stream. failed and cancelled also receive no further live events.

Recovery evidence: Refreshing a completed run immediately shows its final text, analysis blocks, warnings, and documents instead of replaying early output.

Frontend checks fail ​

Treat each command separately:

bash
npm test
npm run lint
npm run format:check
npm run build
1
2
3
4
  • For a test failure, correct the state logic or request contract instead of deleting the assertion.
  • lint includes both code rules and TypeScript checks.
  • For a formatting failure, reformat only the files in your change so unrelated work is not overwritten.
  • For a build failure, start with the first build error instead of the last line.

Automated checking is complete only when all four commands exit with code 0 and the build creates dist/. Chinese and English routes, themes, narrow screens, and long-run refresh still need browser checks. See frontend development for the full change procedure.
