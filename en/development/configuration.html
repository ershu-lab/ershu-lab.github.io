Add a setting: choose the owner and the loading path ​

The difficult part of a new setting is usually not its name. It is ownership and activation. A setting in the wrong module creates a reverse dependency. A runtime setting that is registered but read through the base getter can appear successfully in administration while changing no real behavior.

Choose the owning module first ​

Configuration purposeOwnerCurrent examples
Database, Milvus, repository, and security foundations shared by backend modulesCore SettingsDATABASE_URL, REPOSITORY_STORAGE_PATH, ENCRYPTION_KEY
HTTP, browser Cookies, login rate limiting, access tokens, and API pollingAPI ApiSettingsREDIS_URL, CORS_ORIGINS, POLLER_INTERVAL_SECONDS
Analysis queue, concurrency, LSP, dependency preparation, and user-question policyWorker WorkerSettingsMAX_PARALLEL_REPOSITORY_RUNS, REPOSITORY_LSP_ENABLED
MCP listening, origin, host, and build identityMCP McpSettingsMCP_ALLOWED_HOSTS, MCP_BUILD_COMMIT
Frontend build address and browser behaviorFrontend build configurationAPI base address and frontend build options

Core must not become the owner of every setting merely because the other modules can import it. It explicitly does not own Redis, Cookies, access tokens, Worker analysis policy, or MCP output behavior. API must not depend on Worker or MCP source.

The Worker administration contract is a deliberate boundary. Its 37 definitions live in Core worker_runtime_contract.py so API can display and validate them, while the fields and behavior remain in Worker. Sharing the contract does not move Worker behavior into Core.

Decide whether runtime override is appropriate ​

A setting is a good runtime candidate only when:

  • the change affects later operations and does not rebuild a database connection, HTTP listener, or encryption identity;
  • multiple instances can adopt it over a short refresh window;
  • a precise type, range, and activation note remove ambiguity;
  • returning to the environment value needs only deletion of the database override, not migration of existing data.

Secrets, database and Redis addresses, Cookie names, listening addresses, and production identities should remain startup settings. The API process currently has 11 runtime-overridable settings; the other 37 shown by system administration are consumed by Worker.

Follow the current loading path ​

  1. Core Settings declares shared fields and reads defaults, .env, and the process environment.
  2. API, Worker, and MCP subclasses add module-owned fields.
  3. get_settings(), get_api_settings(), and their peers cache the settings object inside the process.
  4. Each service runs its own validation during startup.
  5. API or Worker reads registered runtime.<name> rows from SystemSetting, validates them, and places them in the process override map.
  6. Business logic calls get_effective_settings() or get_effective_api_settings() to combine startup values with runtime overrides.

Step 6 is essential. Code that keeps calling the cached base getter will ignore a database override even after it has been saved and refreshed.

Add a startup setting ​

For a module-local setting that takes effect after restart:

  1. Add a typed field with a conservative default to the settings class that owns the behavior.
  2. Express ranges in Pydantic field constraints or the module validation function instead of scattering checks among callers.
  3. Document format and purpose in the matching .env.example, without real secrets.
  4. Read it through the module's cached settings entry point; do not import another service's settings class across repositories.
  5. Test the default, a valid environment value, invalid values, and production constraints.
  6. State which process must restart after a change.

An API field belongs in ApiSettings, not Core merely to reuse an existing base class. The same rule applies to Worker and MCP.

Add a runtime-overridable setting ​

In addition to the settings-class field, complete the entire path:

  1. Add a RuntimeSettingDefinition to the owning definition tuple.
  2. Give it a stable internal name, uppercase env_name, administration group, value type, and runtime_note.
  3. Set integer bounds or an explicit unlimited value; list every enum option.
  4. Include that definition group in the service refresh function.
  5. Make the real consumer call the effective settings getter.
  6. If it must appear in API administration, ensure the definition reaches MANAGED_RUNTIME_SETTING_DEFINITIONS.
  7. Test the environment value, database override, reset, invalid input, and activation timing.

Runtime definitions currently support booleans, integers, strings, string lists, string maps, and enums. Generic validation also:

  • rejects a Boolean used as an integer;
  • trims strings and rejects empty or longer-than-255-character values;
  • removes empty list items and limits a list to 50 entries;
  • lowercases and sorts map keys, with at most 50 entries;
  • lowercases enum input before matching the allowed options.

API-owned runtime settings ​

Define them in API_RUNTIME_SETTING_DEFINITIONS and include them in ALL_API_RUNTIME_SETTING_DEFINITIONS. API refresh and system administration already use this union. Consumers must call get_effective_api_settings().

Core-owned runtime settings ​

Define them in CORE_RUNTIME_SETTING_DEFINITIONS. Both API and Worker read this shared group, so inspect consumer sites and tests in both services.

Worker-owned runtime settings ​

Put defaults and the administration contract in Core worker_runtime_contract.py, and the matching fields in Worker WorkerSettings. API only stores and reports the definitions. Worker refreshes them and reads them through get_effective_settings().

Do not move model channels back into environment variables ​

Model providers, addresses, keys, model catalogs, and purposes are managed by API and stored in the database. The current .env.example explicitly says that model channels are configured through administration. Extend the model-channel schema and permission flow for new model capabilities instead of adding old-style global model environment variables.

What to test ​

Cover at least:

  • settings creation from defaults and valid environment values;
  • rejection of wrong types, out-of-range values, and dangerous production combinations;
  • a database override reports source: database, and reset returns to source: environment;
  • a periodic refresh continues to a later cycle after one failure;
  • the business consumer actually uses the effective getter;
  • Worker contract defaults stay aligned with Worker settings fields;
  • security settings such as secrets or host allowlists have rejection tests.

The closest API tests are tests/test_runtime_settings_boundaries.py and tests/test_system_settings.py. Core shared-setting coverage starts in tests/test_core_settings.py and the runtime-setting tests.

Completion criteria ​

  • The field is in the module that owns the behavior, without a new reverse dependency.
  • Environment name, type, default, range, and production constraint have tests.
  • A startup setting states its restart requirement; a runtime setting states which later operations it affects.
  • The value, source, and reset behavior shown by administration match the real consumer.
  • .env.example, types, tests, and documentation use the same name and meaning.
  • Consumer repositories pin the correct shared Core version; while public distribution remains unavailable, the change does not claim that an external user can complete a fresh install.

Source locations ​

  • core/src/ershu/core/config.py: shared settings and security validation.
  • core/src/ershu/services/runtime_settings.py: runtime definitions, generic validation, refresh, and effective Core settings.
  • core/src/ershu/services/worker_runtime_contract.py: Worker defaults and administration contract.
  • api/src/ershu/api/runtime_settings.py: API settings, validation, and effective API settings.
  • api/src/ershu/api/services/system_settings.py: administrator-visible definitions, database writes, and resets.
  • api/src/ershu/api_main.py: API startup validation and periodic refresh.
  • worker/src/ershu/workers/runtime_settings.py: Worker fields, validation, and effective settings.
  • mcp/src/ershu/mcp/runtime_settings.py: MCP fields and production validation.
  • api/tests/test_runtime_settings_boundaries.py and api/tests/test_system_settings.py: API setting-boundary tests.
