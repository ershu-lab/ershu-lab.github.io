Develop the frontend ​

The Ershu frontend is an independent repository. It owns browser UI, browser state, and HTTP requests. It does not import source from Core, API, Worker, or MCP. Before changing a page, confirm the contract through a running Ershu instance and published interfaces. A backend directory that happens to exist beside your checkout must not become an implicit dependency.

Technology and runtime boundary ​

The current frontend uses:

  • Node.js 24;
  • Vite 7;
  • React 19;
  • React Router with hash routing;
  • TypeScript;
  • Tailwind CSS and Radix components; and
  • markdown-it, Mermaid, and graph components.

Hash routing allows static files to host runtime pages. Chinese routes look like #/zh/projects, while English routes look like #/en/projects.

The frontend knows only public HTTP contracts. Queue processing, authorization decisions, document generation, and search behavior remain backend responsibilities. The UI must not turn a local guess into a server fact.

Directory responsibilities ​

PathResponsibility
src/app.tsxRoutes, authentication guards, project layout, and global providers
src/pages/Thin entry points corresponding to routes
src/features/Page controllers, views, and independently testable state logic
lib/api/Request methods and types, cookie handling, and CSRF behavior
lib/api-client.tsAggregation of the API client modules
lib/auth-context.tsxAuthentication state, session restoration, refresh, and sign-out
lib/i18n.tsChinese and English message lookup and locale path parsing
messages/zh.json, messages/en.jsonUI text for both languages
lib/theme-provider.tsxLight, dark, and system theme selection
components/Shared layout and UI components
hooks/Event-stream and shared interaction hooks

Put requests in lib/api/, reusable state under src/features/, and keep src/pages/ focused on composition. A page entry should not own requests, state, rendering, and copy at the same time.

Start the frontend locally ​

In the independent frontend repository, run:

bash
cp .env.example .env.local
npm ci
npm run dev

The development server listens on http://localhost:3000 by default. A successful start leaves the process running, and the browser enters initial administrator setup, sign-in, or the project list instead of showing a static blank page.

The frontend has four build-time settings:

VariableDefaultPurpose
VITE_API_BASE_URL/api/v1Base path for browser API requests
VITE_CSRF_COOKIE_NAMEershu_csrfName of the CSRF cookie
VITE_DEV_API_PROXYhttp://localhost:8000API proxy target in development
VITE_DEV_MCP_PROXYhttp://127.0.0.1:8001MCP proxy target in development

Restart the development server after changing a proxy target. Model names, model API keys, and model-channel endpoints are not build settings; administrators configure them in the web interface.

Add or change a page ​

1. Confirm the interface contract ​

Use the running Ershu MCP, interface documentation, and actual responses to confirm:

  • path and request method;
  • request and response fields;
  • access requirements;
  • failure states; and
  • whether a long task uses a snapshot, event stream, or final result.

You should be able to trace every displayed field to a public response rather than a backend-internal object.

2. Extend the API client ​

Add the request and its types to the appropriate module under lib/api/, then export them through the client entry point. Keep using the shared request layer so cookie, CSRF, error parsing, and session-refresh behavior remain consistent.

Requests that submit a password, token, SSH key, or model API key must also use the existing secure-transport check. Localhost is permitted for development; another hostname requires HTTPS.

The completed method should be importable by feature code, with no page assembling a second API base URL by hand.

3. Put state and views in a feature directory ​

Under src/features/<feature>/, separate:

  • the controller that loads and submits data;
  • the view that presents it;
  • browser-independent state transitions and helpers; and
  • tests for that pure logic.

This makes state transitions, permission-dependent visibility, and failure handling testable without duplicating a page component.

4. Connect the page and route ​

Add a thin entry under src/pages/, then lazy-load it from src/app.tsx. Project pages belong below /:locale/projects/:projectId; global administration pages stay within the existing workspace structure.

Both the Chinese and English URLs should open the page, and an unauthenticated user should still return to the sign-in page in the corresponding locale.

5. Keep Chinese and English copy aligned ​

Add the same message-key structure to messages/zh.json and messages/en.json. Do not hard-code a notice for only one language, and do not leave fallback or degradation messages in English on the Chinese page.

After changing language, the current page and object identifier should remain the same; only the locale segment and UI text should change.

6. Preserve long-running task semantics ​

Run detail must distinguish active and terminal states:

  • an active run loads a snapshot and then connects after its cursor;
  • completed and completed_with_warnings load the final result directly;
  • failed and cancelled do not keep an event stream open; and
  • refreshing the page must not create another run.

Chat on Docs is currently project-scoped. Opening a document does not make a request document- or section-scoped.

Validate the change ​

Run these commands in order before submitting the change:

bash
npm test
npm run lint
npm run format:check
npm run build

Use these acceptance conditions:

  • npm test exits with code 0;
  • npm run lint passes both code and TypeScript checks;
  • npm run format:check lists no file that needs reformatting; and
  • npm run build exits with code 0 and creates dist/.

The current automated suite mainly covers state logic, request contracts, and event processing. It is not a complete browser end-to-end suite. Also check manually:

  • Chinese and English routes;
  • light, dark, and system themes;
  • a narrow viewport around 375 pixels and common desktop widths;
  • keyboard operation and focus;
  • expired authentication, request failures, and empty data;
  • refreshing an active run and loading a completed run.

If a check fails, use development troubleshooting instead of hiding the problem by deleting a test or weakening an interface type.
