Extend MCP and Worker ​

MCP and Worker both depend on Core, but their responsibilities differ. MCP safely exposes existing read-only queries to development agents. Worker reads repositories in the background, extracts facts, builds indexes, and generates documents. Before adding a feature, decide whether it reads an existing result or produces a new one.

When multiple entry points need the same query, put its data and permission rules in Core first. MCP should provide parameter bounds, authenticated invocation, and context-sized output. Do not duplicate business queries in MCP or make Worker read its own results back through MCP.

Add an MCP tool ​

1. Define the shared read operation first ​

A tool that reads projects, repositories, documents, graphs, or contracts should reuse a Core service and response type. Shared services own:

  • project and repository ownership checks;
  • user read or management permission;
  • MCP key project scope;
  • freshness, evidence, and data-availability state; and
  • audit records.

Small navigation logic used only by MCP may remain under mcp/src/ershu/mcp/, but it must still use Core permission and data boundaries.

2. Add an asynchronous wrapper in server.py ​

Use bounded parameter types. A project parameter may accept a UUID, slug, or unique readable name. Pagination, tree depth, source lines, and query length all need explicit upper limits.

Use run_project_tool for project tools; it authenticates and resolves the project reference before calling the service. Use run_session_tool for service-wide tools. If direct session control is required, use authenticated_session and never bypass Authorization: Bearer ....

For a large result, add a dedicated compactor in payload_compaction.py and remove only repeated or low-value fields. Do not discard commit, provenance, authority, freshness, coverage, truncation, or degradation metadata simply to shorten output.

3. Register the tool explicitly ​

Add the function to _registered_tools() in server.py. A defined but unregistered function is invisible to clients. get_server_info.capabilities comes directly from this registry, so the observable registration result is the new name appearing in that call.

4. Complete the security tests ​

At minimum, verify that:

  • a call without a Bearer credential is rejected;
  • a key outside project scope does not reveal whether the project exists;
  • a user without read or management permission is rejected;
  • a repository identifier cannot cross project boundaries;
  • pagination and input limits reject values outside their bounds;
  • audit records contain no query key or repository credential;
  • compacted output still retains revision, evidence, and state; and
  • both _registered_tools() and get_server_info contain the new name.

Add a Worker fact extractor ​

1. Implement the common protocol ​

A general repository fact extractor implements GraphFactExtractor under worker/src/ershu/workers/services/fact_extractors/. It receives a bounded scan context and produces nodes, edges, evidence, unknowns, and metrics. It must not execute repository scripts.

Facts need stable identifiers and a source file, line range, or another anchor that can be verified in source. Record an unknown when evidence is insufficient instead of persisting a guess as a definite relationship.

2. Register the extractor and declare its rules ​

Add the implementation to the extractor registry and declare its rules in the Core knowledge-graph rule pack. Registry validation checks coverage in both directions: an extractor without a rule and a rule without an implementation both fail validation.

Increment the rule-pack version when rule meaning changes, so existing facts can be identified and rebuilt. Do not reuse an old rule identifier for different semantics.

3. Use the dedicated registry for framework routes ​

For static route discovery in another web framework, implement a FrameworkRouteExtractorSpec with the framework name, rule identifier, file suffixes, detection conditions, and scanner, then add it to the framework-route registry. Shared assembly converts routes, operations, handlers, and evidence into consistent facts.

Tests should cover definite matches, dynamic paths, unparseable declarations, and the “route-like but unsupported” signal. An unsupported framework must not disappear silently.

Add a Worker analysis-agent tool ​

Agent tools have one validated registry. A new tool must provide all four parts:

  1. input schema;
  2. executable handler;
  3. result summarizer; and
  4. clear model-facing description.

Registry validation requires the advertised and executable sets to match. A schema without a handler reports a missing handler; a handler without a schema reports a missing schema. Keep the tool read-only, path-bounded, and output-bounded, with explicit unknown and truncation metadata.

Extend LSP language support ​

This requires more than adding an image name. Current adapter groups cover Python, TypeScript/TSX/JavaScript, Go, Rust, C/C++, and Java. A new language spans at least:

  • the Core language and source-suffix registry;
  • Worker LSP adapter groups, default images, and allowed values;
  • Docker read-only, offline, resource-limit, and cleanup behavior;
  • capability probing, dependency preparation, and error states; and
  • setting-boundary, image, protocol, and end-to-end indexing tests.

Dependency preparation and LSP are separate sandboxes. The optional preparation sandbox only downloads supported locked dependencies; LSP remains offline and read-only. Managed lockfile ecosystems currently cover Go, npm, Python, and Cargo. Java Maven and Gradle are not part of this preparation path yet.

Do not stop at exit codes. An MCP extension should appear in a real client's get_server_info response and complete one allowed and one denied call with a scoped key. A Worker extension should generate the expected source-anchored facts from a fixture repository, report unsupported or uncertain input explicitly, and leave the workspace unchanged.

Before committing, inspect MCP and Worker changes separately. Confirm that shared rules were not copied into both modules and that no test-only branch entered a production path.
