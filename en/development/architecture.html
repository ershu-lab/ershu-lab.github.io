Architecture and key data flows ​

Ershu consists of four running processes and one shared package. Core is installed into the API, Worker, and MCP environments; it does not listen on a port by itself.

Core in this diagram is not a network hop. API, Worker, and MCP import its models, authorization, and query services into their own processes.

Boundaries between the five modules ​

Core: shared facts and rules ​

Core defines database models, migrations, project authorization, run state, repository workspaces, retrieval interfaces, model channels, and runtime-setting contracts. Other backend modules can call those public services, but their HTTP and background-process behavior must not move back into Core.

PostgreSQL is the business source of truth: users, projects, repositories, access, queue state, document metadata, and setting overrides are persistent there. Milvus stores vectors used by semantic retrieval. Redis supports short-lived caching, leases, and coordination; it is not the source of run results.

API: the web control plane ​

The API exposes FastAPI routes for OPAQUE login, session cookies, CSRF, project and repository management, model channels, run creation and recovery, documents, search, relationship queries, and administration.

When creating a run, the API checks project access, analysis type, repository scope, and baseline requirements, then uses Core to store run and queue records. It never analyzes code inside the request process. ershu-api-poller is a separate process in the same repository and coordinates scheduled repository checks with a lease.

Worker: the analysis data plane ​

The Worker claims available items from the durable queue, prepares a restricted workspace at the target revision, then builds repository trees, code indexes, knowledge relationships, search indexes, and project documents in stages. It continually stores stage, checkpoint, event, usage, and outcome data so the API can recover state after a disconnected client.

Read-only repository tools enforce path, file-size, and call-budget limits and do not execute repository scripts. Language services run in controlled environments. Language support and dependency preparation are separate concepts: for example, Java language-service support exists, while automated Maven dependency preparation does not.

MCP: the read-only agent surface ​

MCP exposes project resolution, documents, trees, code indexes, relationships, search, and context queries over Streamable HTTP. Each request validates a Bearer credential, then applies key scope and project authorization through Core services.

MCP tools cannot create projects, change repositories, or start runs. State-changing work belongs in the web app or API. The current server registers 27 tools; that count describes this revision and should not become a permanent client constant.

Frontend: the human workspace ​

The frontend is a React single-page application using HTTP and SSE through its API client. It covers login, project selection, repositories and runs, document reading and chat, code search, the knowledge graph, MCP keys, and system administration.

After a refresh, the frontend restores authentication and reads a durable run snapshot from the API. Live events accelerate updates but are not the sole source of state. The frontend does not know about database or Worker instances directly.

The queue record is the recovery boundary. Worker leases prevent two instances from executing the same item concurrently. If an instance disappears, eligible work can become claimable again. A client must inspect final run state; a successful create response does not mean analysis succeeded.

How does incremental analysis preserve a project view? ​

The first full_project run pins revisions for every active repository and establishes the baseline. Later incremental runs process changed repositories and revisions while keeping project-level output. The API rejects incremental requests without a baseline.

Cron polling and webhooks both resolve repository changes before creating an ordinary run. Webhook verification signs the timestamp, a NUL byte, the nonce, another NUL byte, and the raw request body. A proxy or middleware must not rewrite that body first.

Preserve these boundaries when evolving the system: state changes in API, long-running work in Worker, shared data and rules in Core, agent retrieval in MCP, and human interaction in frontend.
