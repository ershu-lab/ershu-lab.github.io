Read this before contributing ​

Ershu business code is split into five modules. A sixth composition repository, also named ershu, provides local integration, infrastructure, and cross-module acceptance checks. Before changing code, identify the module that owns the behavior and open only the boundaries the change needs.

What does each repository own? ​

RepositoryOwnsDoes not own
coreData models, migrations, authorization, run state, retrieval, and shared contractsNo HTTP listener or background worker
apiHTTP routes, web authentication, administration, cron, and webhook entry pointsDoes not execute analysis jobs directly
workerClaiming jobs, preparing read-only workspaces, extracting facts, and generating documents and indexesNo user-facing administration API
mcpAuthenticated, read-only MCP query toolsDoes not change projects, repositories, or run state
frontendLogin, project workspace, run tracking, documents, search, graph, and administration pagesNever reads the database directly
ershuLocked module combination, local infrastructure, cross-repository tests, and release boundariesDoes not copy business implementations from the five modules

API, Worker, and MCP depend on Core, but they must not couple to one another through source imports. The frontend communicates with the API over HTTP. A change that crosses modules needs a complete acceptance check in the composition repository.

Recommended order for a feature change ​

  1. State the external behavior and failure modes, then locate the existing contract or test.
  2. If the change affects shared data or authorization, update Core models, services, and migrations first.
  3. Implement the entry point in its owner: HTTP in API, analysis in Worker, read-only agent retrieval in MCP.
  4. Use the frontend API client and handle loading, empty, error, and forbidden states.
  5. Run the owning module's formatting, type, test, and build checks, then run the composition boundary and workflow tests.
  6. Update only the documentation affected by the behavior and include a verification outcome.

Common starting points ​

  • To understand calls and ownership, read Architecture and data flow.
  • For a first setup, read Set up local development.
  • To add a setting, read Configuration flow.
  • To add an HTTP endpoint, read Add an API.
  • To add a tool or analysis stage, read Extend MCP and Worker.
  • To add a page, read Build a frontend page.
  • Before committing, read Quality and contributions.

Minimum bar before handoff ​

  • The change lives in the module that owns the responsibility, with tests for any shared contract.
  • A new setting has a type, default, runtime-override decision, and useful error feedback.
  • A new API has authentication, authorization, input, and failure-path tests.
  • Long-running work remains inspectable after a browser disconnect.
  • Documentation describes current behavior, and any claimed command result was actually observed.
  • The owning repository passes its checks; cross-repository work also passes composition tests.

Sources: AGENTS.md, dependency manifests, import-boundary tests, entry points, and CI workflows across all six repositories.
