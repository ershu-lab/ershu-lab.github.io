Add an API endpoint: complete the boundary, permission, and test work ​

An endpoint is more than a path and response. It decides who can call it, which module owns the data, how failure is represented, and whether Cookies, MCP keys, and project permissions stay inside their intended boundaries.

First confirm that the feature belongs to API ​

API owns HTTP, browser login, Cookies, CSRF, status-code mapping, chat, streaming, and web administration. Do not put these changes directly into API:

ChangeStart in
Shared data model, migration, permission rule, or queryCore
Analysis execution, indexing, LSP, or model orchestrationWorker
MCP tool or output formatMCP
Page, interaction, or browser stateFrontend

API may depend only on a pinned Core version, never on Worker or MCP. If a new endpoint needs a shared field, first add the Core model and migration and complete Core tests. Then update API's pinned Core commit to the version containing that change.

Follow the existing four layers ​

LayerDirectoryResponsibility
Request and response modelsapi/src/ershu/api/schemas/Fields, types, lengths, and basic format
Business servicesapi/src/ershu/api/services/Post-identity business rules, database operations, and audit
HTTP routesapi/src/ershu/api/routes/Path, method, dependencies, and response model
Root routerapi/src/ershu/api/router.pyRegisters each subrouter in the unified API

api_main.py mounts the root router under /api/v1. A subrouter should declare only its own relative prefix rather than repeating the version path.

The current system-settings endpoint is a concrete end-to-end reference:

  • models: schemas/system_settings.py;
  • business logic: services/system_settings.py;
  • routes: routes/system_settings.py;
  • registration: system_settings.router in router.py;
  • final paths: GET and PATCH /api/v1/admin/system-settings, plus DELETE /api/v1/admin/system-settings/{name}.

It also shows administrator identity, a database session, input validation, audit, commit, and response reread working together. Follow the separation for the new behavior; do not copy the whole file blindly.

Choose the correct identity dependency ​

DependencyAccepted identityUse it for
current_userBrowser session or user Bearer token; rejects MCP keysNormal web-user endpoints
current_auth_contextUser token or MCP keyRead endpoints that intentionally support MCP and continue to enforce project and key scope
admin_userAdministrator userUser, global setting, credential, and other administration endpoints
reject_mcp_key_authExplicitly rejects an MCP key after building an auth contextAudit logs, key management, and other actions that require a real user

Authentication is not resource authorization. Project routes must still call Core project-membership and permission services. MCP-capable routes must restrict both project and capability to the key's scope.

An endpoint without an identity dependency needs a clear reason. Health is a public liveness signal. A repository webhook instead uses its own timestamp, nonce, and HMAC signature. /api/v1/webhooks/ is excluded from browser CSRF middleware, so the webhook route's signature validation is mandatory.

Validate input in the right layer ​

  • Put field type, requiredness, length, and structure in Pydantic models. Request parsing failures of this kind normally return 422.
  • Put conflicts, permissions, and state rules that require database reads in the service layer.
  • Call existing Core services for shared rules instead of writing an approximate copy in a route.
  • Preserve original bytes when verification depends on the exact request body, as webhook signatures do.

get_session() provides a database session but does not automatically commit business changes. Follow the matching service pattern and handle writes, audit, commit, and failure cleanup explicitly. Tests should prove that a failed operation leaves no partial result.

Use the common error meanings ​

API maps Core ErshuError kinds to a consistent JSON error response:

invalid_input400

not_found404
conflict409

Do not return 500 for user input, and do not handcraft a different error body in every route merely to choose a status. Add a stable machine-readable code only when clients need a branch, as the tested csrf_invalid response does.

Register the route and check path conflicts ​

  1. Give the subrouter an appropriate APIRouter prefix.
  2. Import and register it exactly once in api/src/ershu/api/router.py.
  3. Check whether a static path can be consumed first by a dynamic path such as /{id}.
  4. Assign a tag consistent with the existing API navigation.
  5. In development, inspect /docs and confirm the method, final /api/v1 path, request model, and response model.

/docs exists only under ENVIRONMENT=development. Seeing a route there does not prove that its permission and transaction behavior is correct; tests remain authoritative.

Test four result classes ​

API repository policy requires every new or changed route to cover at least:

  1. Success: status, response model, database change, and audit result are correct.
  2. No permission: unauthenticated callers, regular users, wrong project members, or insufficient MCP scope are rejected correctly.
  3. Invalid input: wrong types, boundary values, state conflicts, and missing resources return stable statuses.
  4. Security: CSRF on Cookie writes, webhook signatures, credential exposure, or another endpoint-specific boundary.

Tests normally use FastAPI TestClient with a temporary SQLite database for route behavior. Add a real PostgreSQL integration check for PostgreSQL-specific migrations or constraints; SQLite alone cannot prove them.

Also check that:

  • responses do not expose tokens, ciphertext, private keys, or internal exception details;
  • repeated submissions have a clear idempotent or conflict result;
  • a failed write leaves the session usable and no partial commit behind;
  • API tests do not import ershu.workers, ershu.mcp, or test helpers from another repository.

Developers must run and record these checks; this page does not claim that they have passed. API currently pins Core to a private source, so a public environment without access cannot complete a fresh dependency installation. Treat that as a distribution prerequisite rather than inventing a public address.

Completion criteria ​

  • The route owns only the HTTP boundary, business rules live in services, and shared rules live in Core.
  • The final path is registered once under the intended /api/v1 location.
  • Identity and resource authorization are explicit; an MCP key cannot accidentally gain user or administrator capabilities.
  • Pydantic parsing failures and business errors have stable, distinct meanings.
  • Success, no-permission, invalid-input, and security paths all have tests.
  • Commit, audit, and failure cleanup for writes have verifiable results.
  • Actual execution records, rather than documentation assumptions, show the full API tests, lint, format check, and build results.

Source locations ​

  • api/src/ershu/api/router.py and api/src/ershu/api_main.py: route registration and the /api/v1 prefix.
  • api/src/ershu/api/deps.py: user, administrator, and MCP identity dependencies.
  • api/src/ershu/api/database.py: request database session.
  • api/src/ershu/api/error_handlers.py: common error-status mapping.
  • api/src/ershu/api/schemas/system_settings.py: existing request and response model example.
  • api/src/ershu/api/services/system_settings.py: existing business, audit, commit, and reread example.
  • api/src/ershu/api/routes/system_settings.py: existing administrator route example.
  • api/src/ershu/api/services/repositories/triggers.py: webhook security outside Cookie authentication.
  • api/AGENTS.md: module boundaries and route test requirements.
  • api/pyproject.toml: test and build entry points and the pinned Core source.
