Problems Ershu can solve ​

Ershu organizes project context before people or AI ask a question. Each use case below maps to a feature you can test in your own project.

AI coding: spend less time rebuilding context ​

Coding agents often struggle with project conventions rather than syntax. An agent may see the current repository but miss an interface defined by another service. It may read an old document without knowing which commit that document describes.

Ershu exposes project-scoped, read-only MCP tools. A client can discover a project and then retrieve:

  • project overviews and wiki sections;
  • repository trees, code indexes, and bounded sections of source;
  • project search, relationships, candidate change surfaces, and static runtime paths;
  • public interfaces, consumer contracts, and schemas;
  • commit, freshness, coverage, fallback, and truncation signals.

This does not guarantee correct code. It helps an agent see project boundaries sooner and gives reviewers a better answer to the question, "Where did that conclusion come from?"

A safer reading order ​

  1. Use MCP to identify the project, repositories, and current commits.
  2. Read the project overview and relevant wiki sections for direction.
  3. Narrow the area with search, relationships, or interface contracts.
  4. Read the critical source last, then run the real tests locally.

This sequence is easier to control than placing a large set of files into the prompt at once, and it avoids much of the code that has nothing to do with the task.

Internal wiki: make code knowledge useful to the whole team ​

Repository knowledge affects more than the people writing code. Why a feature fails, where a field comes from, and who consumes an interface also matter to QA, product, support, delivery, and architecture work.

RoleWhat the wiki can provide firstWhat still needs verification
New developerProject shape, repository responsibilities, entry points, and main workflowsCurrent source, tests, and historical context from maintainers
MaintainerConfiguration, module relationships, interfaces, and source citationsThe actual branch, commit, and change under review
QA engineerInterfaces, schemas, message channels, and failure pathsA running environment, test data, and acceptance rules
Product and supportWhich modules deliver a feature, related documents, and searchable termsBusiness rules, customer agreements, and release notes
Architecture and securityRepository relationships, public entry points, candidate dependencies, and access boundariesRuntime evidence, security tests, and deployment configuration

Wiki pages support Markdown, Mermaid diagrams, table-of-contents navigation, and source previews. Documents are grouped by repository and category, while one Ershu project can contain several repositories. The wiki is a shared starting point, not a replacement for source.

Cross-repository changes: find the likely impact before editing ​

Many enterprise systems are divided by repository but shipped as one product. A change can start in the frontend, cross an API or message, pass through a service and schema, then affect a consumer owned by another team.

Ershu brings those clues into one project:

  • the knowledge graph displays repository, directory, symbol, and dependency relationships;
  • change-surface queries find direct and related candidates around a path or symbol;
  • static runtime paths organize possible steps through calls and stored relationships;
  • interface contracts separate providers, consumers, public interfaces, and schemas;
  • cross-repository search can cover the whole project or one selected repository.

Use these results to narrow the review area. Dynamic calls, reflection, runtime configuration, and external systems may not appear in static data, so releases still need tests and human review.

Handoffs and legacy systems: search the project before asking one person ​

When a key maintainer leaves or a team inherits a poorly documented system, writing a new wiki by hand begins with a long source investigation. Ershu can build an initial view from current repositories, giving later interviews and manual notes a shared structure.

A practical workflow looks like this:

  1. Put the repositories that ship together into one project.
  2. Complete the first full-project analysis.
  3. Ask current maintainers to review the important documents and relationships, then add reasons and constraints that code cannot express.
  4. Turn recurring questions into wiki reading paths or MCP guidance.
  5. Use later runs and repository triggers to keep the factual layers current.

Ershu can reconstruct what the code says now. It cannot recover business history that was never recorded in code, commits, or documents.

Useful features that are easy to miss ​

1. Interface contracts are queryable on their own ​

Ershu organizes facts from OpenAPI, GraphQL, Protobuf, Thrift, AsyncAPI, message channels, database schemas, generated clients, and selected framework routes. MCP clients can query consumer contracts, public interfaces, schemas, and recorded contract differences.

2. Results report their own limits ​

Search and relationship queries return the actual mode, fallback reason, coverage, status, and truncation signals. Documents and repository facts carry commit and freshness data. An empty result no longer has to mean "nothing exists"; the data may be missing, stale, or outside the current query boundary.

3. The analysis itself is inspectable ​

Run details retain stages, timelines, tool results, warnings, and model usage. Durable run state supports recovery after interruption, and closing the browser does not cancel the background job.

4. Team access and agent access are managed separately ​

The web app uses users, project membership, and additional grants. An MCP key belongs to a user, can be limited to one or more projects, and may have an expiration time. It never expands the project access of the person who created it.

5. Models are not hard-coded in deployment files ​

Administrators configure language-model, embedding, and reranker channels in the web app. Provider types include OpenAI, OpenAI-compatible services, DeepSeek, and Anthropic. Whether code reaches an external service depends on the channels the team enables.

When it may not be worth deploying yet ​

  • The project is one small repository with clear boundaries and a team that already knows it well.
  • The team only needs one-time local search and has no reason to share the result.
  • The environment cannot provide PostgreSQL, Milvus, a Worker, and model channels.
  • The expected outcome is proof of every runtime behavior or a replacement for testing and review.
  • Nobody is prepared to define model, network, credential, and repository-path trust boundaries for private code.

If the earlier scenarios match your team, run the one-machine deployment on a non-critical project and test it with a real cross-repository question.
