What Ershu is

On this page

What Ershu is, where it fits, and where it stops ​

Ershu is a self-hosted code-understanding and context service. It analyzes the GitHub, GitLab, or trusted local repositories in a project as one system, builds documentation, retrieval indexes, and code relationships, then exposes the results through a web app, HTTP API, and MCP.

MCP, the Model Context Protocol, is a standard way for development agents to use external tools and data. Ershu's MCP service is a read-only query surface; it does not modify repositories.

What does an analysis produce? ​

ResultPurposeAvailable through
Repository trees and file factsConfirm paths, file types, and the analyzed revisionWeb, API, MCP
Structured project documentsUnderstand modules and workflows by topicWeb, API, MCP
Lexical and semantic indexesFind code by name, text, or meaningWeb, API, MCP
Knowledge relationshipsExplore links between symbols and filesWeb, API, MCP
Run history and checkpointsFollow stages, usage, outcomes, and failuresWeb, API

The Worker reads analysis workspaces through restricted, read-only tools and does not execute repository scripts. Generated documentation requires an enabled model channel. Deterministic repository facts and some indexing work are separate from model-generated output.

How does it fit into daily work? ​

  1. An administrator creates the first account, configures a model channel, and grants project access.
  2. A project member adds repositories and first runs a full-project analysis across every active repository.
  3. The Worker prepares a read-only workspace, extracts facts, and produces project-level results in the background.
  4. People use the web app to read, search, and explore relationships. Development agents query the same project with a scoped MCP key.
  5. Later commits can trigger incremental analysis. Cron polling and signed webhooks arrive through the API; the Worker still performs the analysis.

The first run must be a full-project run. Until that baseline exists, the API rejects incremental runs so that partial output is not mistaken for a complete project view.

Who is it for? ​

  • Teams maintaining systems spread across several repositories;
  • Developers learning unfamiliar code or tracing an explanation back to its implementation;
  • Owners who need controlled, attributable context for development agents;
  • Organizations that want repository credentials, project access, and model settings to remain in their own infrastructure.

Boundaries to understand first ​

  • Ershu currently requires a maintainer deployment. A complete install cannot yet be assembled only from public packages because the composition and backend repositories still reference private Git sources.
  • Generated material helps people understand code; it does not replace source, tests, or review. Resolve conflicting statements against the current implementation.
  • /health confirms that a process is alive, not that every dependency is ready. Check the database, Milvus, model channel, and Worker separately.
  • Creating a run through the API only queues it. No running Worker means no completed analysis.
  • Semantic retrieval requires working Milvus and embedding configuration. Semantic mode does not silently become lexical search; hybrid mode may report an explicit fallback.
  • Only administrators can configure local repositories, and each path must be in a trusted location.

If these conditions fit your environment, continue to Features in context. When preparing a deployment, begin with Basic configuration.
