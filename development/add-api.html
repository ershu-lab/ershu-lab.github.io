新增 API：从边界、权限到测试一次做完整 ​

一个端点不仅是路径和返回值。它还决定谁能访问、数据归谁维护、失败怎样表达，以及 Cookie、MCP 密钥和项目权限是否处在正确边界。

第一步：确认功能确实属于 API ​

API 负责 HTTP、网页登录、Cookie、CSRF、状态码映射、聊天、实时输出和网页后台。以下改动不应直接塞进 API：

改动应先去哪里
共享数据模型、迁移、权限规则或查询Core
分析执行、索引、LSP 或模型编排Worker
MCP 工具和输出格式MCP
页面、交互和浏览器状态Frontend

API 只能依赖固定版本的 Core，不能导入 Worker 或 MCP。若新接口需要共享字段，先在 Core 增加模型与迁移并完成 Core 测试，再把 API 的 Core 固定提交更新到包含该改动的版本。

沿用现有四层结构 ​

层目录职责
请求与响应类型api/src/ershu/api/schemas/字段、类型、长度和基本格式
业务服务api/src/ershu/api/services/权限后的业务规则、数据库操作和审计
HTTP 路由api/src/ershu/api/routes/路径、方法、依赖和响应模型
总路由api/src/ershu/api/router.py把子路由登记到统一 API

总路由由 api_main.py 挂到 /api/v1。子路由只写自己负责的相对前缀，避免重复拼接版本路径。

现有系统设置接口是一条可以核对的完整链路：

  • 类型：schemas/system_settings.py；
  • 业务：services/system_settings.py；
  • 路由：routes/system_settings.py；
  • 登记：router.py 中的 system_settings.router；
  • 最终路径：GET 和 PATCH /api/v1/admin/system-settings，以及 DELETE /api/v1/admin/system-settings/{name}。

它还展示了管理员依赖、数据库会话、输入校验、审计、提交和响应重读怎样协作。新增端点应按自己的业务复用这种分工，而不是复制整个文件。

选择正确的身份依赖 ​

依赖接受的身份适用场景
current_user网页会话或用户 Bearer 令牌；拒绝 MCP 密钥普通网页用户接口
current_auth_context用户令牌或 MCP 密钥明确支持 MCP 调用，并继续检查项目和密钥范围的只读接口
admin_user管理员用户用户、全局配置、凭据等管理接口
reject_mcp_key_auth在已有身份上下文上额外拒绝 MCP 密钥审计日志、密钥管理等只能由真实用户执行的操作

身份认证不等于资源授权。项目接口还要调用 Core 的项目成员与权限服务，MCP 接口还要按密钥范围限制项目和能力。

没有身份依赖的端点必须有清楚理由。例如健康检查是公开存活信号，仓库 Webhook 则依靠自己的时间戳、Nonce 和 HMAC 签名。/api/v1/webhooks/ 被浏览器 CSRF 中间件排除，所以 Webhook 路由自身的签名校验不能省略。

把输入校验放在合适层 ​

  • 字段类型、必填项、长度和结构放在 Pydantic 类型中；这类请求解析失败通常返回 422。
  • 需要查数据库才能判断的冲突、权限或状态规则放在服务层。
  • Core 已有的共享规则直接调用 Core 服务，不要在路由中写一份近似副本。
  • 外部请求正文需要保持原始字节时，例如 Webhook 签名，不要在校验前重新序列化。

get_session() 只提供数据库会话，不会自动替业务提交。服务必须像同类现有代码一样明确处理写入、审计、提交和失败清理，测试也要证明失败时没有留下半成品。

使用统一错误含义 ​

API 会把 Core 的 ErshuError 映射为统一 JSON 错误。当前对应关系是：

错误种类HTTP 状态
invalid_input400
unauthenticated401
permission_denied403
not_found404
conflict409
gone410
rate_limited429
internal500
upstream_failure502
unavailable503

不要用 500 表达用户输入错误，也不要为了返回某个状态码而在每个路由手写不同错误结构。只有稳定的机器分支需要额外错误代码时，才像 CSRF 的 csrf_invalid 一样明确设计并测试。

登记路由并检查路径冲突 ​

  1. 在子路由中声明合适的 APIRouter 前缀。
  2. 在 api/src/ershu/api/router.py 中引入并登记一次。
  3. 检查静态路径是否会被 /{id} 之类的动态路径提前匹配。
  4. 给路由分配与现有导航一致的标签。
  5. 在开发环境查看 /docs，确认方法、最终 /api/v1 路径、请求类型和响应类型正确。

/docs 只在 ENVIRONMENT=development 时存在。文档页面能显示路由，不代表权限和事务已经正确，仍要以测试为准。

为四类结果写测试 ​

API 仓库约定：新增或修改路由至少覆盖以下情况。

  1. 成功：状态码、响应类型、数据库变化和审计结果都正确。
  2. 无权限：未登录、普通用户、错误项目成员或范围不足的 MCP 密钥被正确拒绝。
  3. 输入错误：类型错误、边界值、资源状态冲突和不存在对象得到稳定状态码。
  4. 安全检查：Cookie 写请求的 CSRF、Webhook 签名、凭据泄漏或与端点相关的其他安全边界。

测试通常用 FastAPI TestClient 和临时 SQLite 数据库覆盖接口行为。涉及 PostgreSQL 特有迁移或约束时，应另加真实 PostgreSQL 集成检查，不能只用 SQLite 推断。

还要检查：

  • 响应中没有返回令牌、密文、私钥或内部异常详情；
  • 多次提交的幂等性或冲突含义清楚；
  • 写入失败后会话可继续使用，且没有部分提交；
  • API 测试没有导入 ershu.workers、ershu.mcp 或其他仓库的测试辅助代码。

完成判据 ​

  • 路由只承担 HTTP 边界，业务规则位于服务层，共享规则位于 Core。
  • 最终路径只登记一次，并位于 /api/v1 下的预期位置。
  • 身份依赖与资源权限都明确；MCP 密钥不会意外获得用户或管理员能力。
  • Pydantic 输入错误与业务错误使用稳定且不同的状态含义。
  • 成功、无权限、错误输入和安全路径都有测试。
  • 写操作的提交、审计和失败清理都有可验证结果。
  • API 的完整测试、代码检查、格式检查和构建由实际执行记录证明，而不是由文档假定。

源码位置 ​

  • api/src/ershu/api/router.py、api/src/ershu/api_main.py：路由登记与 /api/v1 前缀。
  • api/src/ershu/api/deps.py：用户、管理员和 MCP 身份依赖。
  • api/src/ershu/api/database.py：请求数据库会话。
  • api/src/ershu/api/error_handlers.py：统一错误状态映射。
  • api/src/ershu/api/schemas/system_settings.py：现有请求与响应类型例子。
  • api/src/ershu/api/services/system_settings.py：现有业务、审计、提交和重读例子。
  • api/src/ershu/api/routes/system_settings.py：现有管理员路由例子。
  • api/src/ershu/api/services/repositories/triggers.py：不依赖 Cookie 的 Webhook 安全边界。
  • api/AGENTS.md：模块边界和路由测试要求。
  • api/pyproject.toml：测试、构建入口与固定 Core 依赖。
