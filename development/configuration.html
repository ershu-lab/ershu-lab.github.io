新增配置项：放对模块并接入正确加载流程 ​

新增配置时，先处理归属和生效方式。一个放错模块的设置会制造反向依赖；一个只登记、不从有效设置入口读取的运行时设置，会在管理页面显示成功，却不改变实际行为。

先决定由哪个模块拥有 ​

配置用途应放位置当前例子
多个后端模块共享的数据库、Milvus、仓库、安全基础设置Core 的 SettingsDATABASE_URL、REPOSITORY_STORAGE_PATH、ENCRYPTION_KEY
HTTP、浏览器 Cookie、登录限流、访问令牌、API 轮询器API 的 ApiSettingsREDIS_URL、CORS_ORIGINS、POLLER_INTERVAL_SECONDS
分析队列、并发、LSP、依赖准备和提问策略Worker 的 WorkerSettingsMAX_PARALLEL_REPOSITORY_RUNS、REPOSITORY_LSP_ENABLED
MCP 监听地址、来源、主机和构建身份MCP 的 McpSettingsMCP_ALLOWED_HOSTS、MCP_BUILD_COMMIT
前端构建时地址与网页行为Frontend 的构建配置API 基础地址和前端构建选项

Core 不能因为“其他模块也能导入它”就收纳所有设置。它明确不拥有 Redis、Cookie、访问令牌、Worker 分析策略或 MCP 输出行为。API 也不能依赖 Worker 或 MCP 源码。

Worker 的在线管理契约是一个特殊边界：37 项 Worker 定义放在 Core 的 worker_runtime_contract.py，让 API 可以展示和校验它们；字段和实际消费仍在 Worker。契约共享不等于把 Worker 行为搬进 Core。

再决定是否允许在线覆盖 ​

只有满足下面条件的设置才适合进入数据库运行时设置：

  • 改动只影响后续操作，不要求重建数据库连接、HTTP 监听器或加密身份；
  • 多实例可以在短暂刷新延迟内逐步采用新值；
  • 可以用明确类型、范围和生效说明避免歧义；
  • 恢复环境值时，只需删除数据库覆盖，不需要迁移已有数据。

密钥、数据库地址、Redis 地址、Cookie 名称、监听地址和生产身份不适合在线改动。当前 API 进程只有 11 项可在线覆盖设置；系统管理接口显示的另外 37 项由 Worker 消费。

当前加载流程 ​

  1. Core Settings 声明共享字段，并读取默认值、.env 和进程环境。
  2. API、Worker 与 MCP 通过继承增加本模块字段。
  3. get_settings()、get_api_settings() 等入口在进程内缓存设置对象。
  4. 各服务在启动时运行自己的校验函数。
  5. API 或 Worker 从 SystemSetting 表读取已登记的 runtime.<name> 行，校验并放入进程内覆盖表。
  6. 实际业务代码通过 get_effective_settings() 或 get_effective_api_settings() 读取“启动值加运行时覆盖”的结果。

第 6 步不能省略。若业务代码继续调用基础的缓存设置入口，数据库覆盖即使已经保存和刷新，也不会影响该逻辑。

增加一个启动设置 ​

以模块本地、重启后生效的设置为例：

  1. 在拥有该行为的设置类中增加带类型和保守默认值的字段。
  2. 若有范围约束，用 Pydantic 字段约束或模块校验函数表达，避免只在调用处临时判断。
  3. 在对应 .env.example 中说明格式和用途，但不要放真实密钥。
  4. 从模块的缓存设置入口读取，不要跨仓库导入另一个服务的设置类。
  5. 增加默认值、环境值、非法值和生产约束测试。
  6. 明确告诉使用者：修改后需要重启哪个进程。

如果该字段属于 API，就放在 ApiSettings，而不是为了复用已有基类把它塞进 Core。Worker 和 MCP 同理。

增加一个可在线覆盖设置 ​

除了设置类字段，还要完成一条完整链路：

  1. 在对应运行时定义元组增加 RuntimeSettingDefinition。
  2. 设置稳定的内部 name、大写 env_name、管理分组、值类型和 runtime_note。
  3. 为整数设置最小值、最大值或明确的无限值；为枚举列出选项。
  4. 让服务刷新函数包含这组定义。
  5. 让真正使用该值的代码调用有效设置入口。
  6. 若要在 API 管理页面出现，确认定义进入 MANAGED_RUNTIME_SETTING_DEFINITIONS。
  7. 测试环境值、数据库覆盖、重置、非法输入和生效时机。

运行时定义当前支持：布尔值、整数、字符串、字符串列表、字符串映射和枚举。通用校验还会：

  • 拒绝把布尔值当作整数；
  • 去掉字符串首尾空白，并拒绝空字符串和超过 255 个字符的值；
  • 清理列表空项，并把列表限制在 50 项；
  • 把映射键转成小写并排序，最多保留 50 项；
  • 把枚举值转成小写后与允许选项比较。

API 所有的运行时设置 ​

在 API_RUNTIME_SETTING_DEFINITIONS 中定义，并加入 ALL_API_RUNTIME_SETTING_DEFINITIONS。API 的刷新函数和系统设置管理服务已经读取这个组合。消费位置必须使用 get_effective_api_settings()。

Core 所有的运行时设置 ​

在 CORE_RUNTIME_SETTING_DEFINITIONS 中定义。API 与 Worker 都会读取这组共享定义，因此变更要同时检查两个服务的使用位置和测试。

Worker 所有的运行时设置 ​

默认值和管理契约放在 Core 的 worker_runtime_contract.py，对应字段放在 Worker 的 WorkerSettings。API 只保存并展示定义；Worker 自己刷新并通过 get_effective_settings() 使用它们。

不要把模型通道改回环境变量 ​

模型提供方、地址、密钥、可用模型和用途由 API 管理并存入数据库。当前 .env.example 也明确说明模型通道通过管理接口配置。新增模型能力时应扩展模型通道结构和权限流程，不要添加一组旧式的全局模型环境变量。

测试什么 ​

至少覆盖：

  • 默认值与合法环境值能创建设置；
  • 非法类型、越界值和生产环境危险组合被拒绝；
  • 数据库覆盖的 source 为 database，重置后回到 environment；
  • 周期刷新失败后仍会继续下一轮；
  • 业务消费者确实从有效设置入口读取；
  • Worker 契约默认值与 Worker 设置类保持一致；
  • 密钥或主机列表等安全设置有拒绝路径测试。

API 仓库当前最接近这条链路的测试是 tests/test_runtime_settings_boundaries.py 和 tests/test_system_settings.py。Core 的共享设置测试在 tests/test_core_settings.py 及运行时设置相关测试中。

完成判据 ​

  • 字段位于实际拥有该行为的模块，没有新增反向依赖。
  • 环境变量名称、类型、默认值、范围和生产约束都有测试。
  • 静态设置明确要求重启；在线设置明确说明影响哪些后续操作。
  • 管理接口显示的值、来源和重置行为与实际消费者一致。
  • .env.example、类型、测试和文档使用同一名称与含义。
  • 消费仓库声明了正确的 Core 最低版本与上限，并重新生成锁文件。

源码位置 ​

  • core/src/ershu/core/config.py：共享设置和安全校验。
  • core/src/ershu/services/runtime_settings.py：运行时定义、通用校验、刷新和有效 Core 设置。
  • core/src/ershu/services/worker_runtime_contract.py：Worker 默认值和管理契约。
  • api/src/ershu/api/runtime_settings.py：API 设置、校验和有效 API 设置。
  • api/src/ershu/api/services/system_settings.py：管理员可见定义、数据库写入与重置。
  • api/src/ershu/api_main.py：API 启动校验和周期刷新。
  • worker/src/ershu/workers/runtime_settings.py：Worker 字段、校验和有效设置。
  • mcp/src/ershu/mcp/runtime_settings.py：MCP 字段和生产校验。
  • api/tests/test_runtime_settings_boundaries.py、api/tests/test_system_settings.py：API 设置边界测试。
