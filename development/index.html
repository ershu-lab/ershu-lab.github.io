参与开发前先读这里 ​

Ershu 的业务代码分成五个模块，另有一个同名组合仓库用于本地联调、基础设施和跨模块验收。开始修改前，先确认需求属于哪个模块，再只打开必要边界。

六个仓库分别负责什么？ ​

仓库职责不应承担的职责
core数据模型、数据库升级、权限、运行状态、检索与共享契约不监听 HTTP，不启动后台任务
apiHTTP 路由、网页认证、管理操作、Cron 与 Webhook 入口不直接执行分析任务
worker领取任务、准备只读工作区、提取事实、生成文档与索引不暴露面向用户的管理 API
mcp认证并提供只读 MCP 查询工具不修改项目、仓库或运行状态
frontend登录、项目工作区、分析跟踪、文档、搜索、关系图和管理页面不绕过 API 直接访问数据库
ershu固定模块组合、本地基础设施、跨仓测试和发布边界不复制五个模块的业务实现

API、Worker 和 MCP 依赖 Core，但彼此不应通过源码导入耦合。前端只通过 HTTP 与 API 通信。跨模块行为需要在组合仓库做一次完整验收。

修改一项功能的推荐顺序 ​

  1. 写清楚对外行为和失败方式，找到当前契约或测试。
  2. 如果涉及共享数据或权限，先修改 Core 的模型、服务和升级记录。
  3. 在唯一负责的进程中实现入口：HTTP 放 API，分析放 Worker，只读智能体查询放 MCP。
  4. 前端调用现有 API 客户端，并处理加载、空状态、错误和权限不足。
  5. 先跑模块自己的格式、类型、测试和构建检查，再跑组合仓库的边界与流程测试。
  6. 更新与行为直接相关的文档，标明验证方法和成功结果。

常见开发入口 ​

  • 需要理解调用关系：阅读整体架构与数据流。
  • 第一次搭环境：阅读搭建本地开发环境。
  • 增加设置：阅读理解配置加载流程。
  • 增加 HTTP 端点：阅读新增 API。
  • 增加工具或分析阶段：阅读扩展 MCP 与 Worker。
  • 增加页面：阅读开发前端页面。
  • 准备提交：阅读质量与提交流程。

提交前的最低要求 ​

  • 变更只落在拥有该职责的模块，必要的共享契约有配套测试；
  • 新配置明确类型、默认值、是否可在线覆盖及错误反馈；
  • 新 API 有认证、权限、输入和错误路径测试；
  • 长任务可以恢复查看，不依赖浏览器连接一直存在；
  • 文档只描述当前实现，命令结果来自实际执行；
  • 每个仓库自己的检查通过，跨仓改动再通过组合仓测试。

事实来源：六个仓库的 AGENTS.md、依赖清单、导入边界测试、入口文件和持续集成配置。
