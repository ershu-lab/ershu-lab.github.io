质量、提交与 Pull Request ​

Ershu 的六个仓库各自独立检查。先验证拥有改动的模块，再验证消费它的模块，最后验证组合仓库。不要用一次跨仓测试掩盖某个模块自己的失败。

怎样为改动选择测试？ ​

改动至少覆盖
数据模型或升级记录新旧数据库升级、模型读写、消费模块契约
权限或认证允许、拒绝、跨项目、过期与重放路径
运行队列创建、领取、续租、失联恢复、取消与最终状态
搜索或索引空结果、范围过滤、来源位置、外部依赖失败与明确回退
MCP 工具输入约束、密钥范围、项目权限、输出上限和来源
前端页面加载、空状态、错误、权限不足、刷新恢复和窄屏布局
配置项默认值、合法边界、非法输入、在线覆盖和敏感值遮盖

先写能够复现行为的最小测试。修复后再跑模块完整检查，避免只验证一个顺利路径。

提交怎样拆分？ ​

一个提交只完成一个可以解释和回退的变化。例如：

  1. 共享模型和升级；
  2. API 或 Worker 行为；
  3. 前端交互；
  4. 文档与部署说明。

跨仓改动不可能成为一个 Git 提交，因此提交说明要写出依赖顺序和匹配提交。不要混入格式化无关文件、临时日志、真实凭据或本地环境文件。

提交前再次运行 git status --short 和 git diff --check，确认只包含计划内文件。已有未提交修改属于当前开发者；除非明确负责，不要覆盖、暂存或整理它们。

Pull Request 应说明什么？ ​

  • 用户能观察到的变化和没有变化的边界；
  • 受影响的仓库、接口、配置和数据升级；
  • 风险最大的失败路径以及对应测试；
  • 实际执行的命令和真实结果；
  • 需要按顺序合并或发布的其他仓库提交；
  • 新密钥、外部服务、数据迁移或回滚步骤；
  • 页面变化的桌面端、移动端和亮暗主题截图。

评审者应能仅凭说明重现验证过程。尚未运行的检查要明确写“未运行”及原因，不能用预计结果代替。

事实来源：六个仓库的 AGENTS.md、安装清单、测试标记和持续集成工作流。
