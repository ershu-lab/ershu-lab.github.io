本页内容

开发故障排查 ​

排查 Ershu 时，先确认问题停在哪一层：依赖安装、基础设施、API、Worker、前端，还是某次运行的产物。不要因为一个存活检查通过，就假定整个分析链路都正常。

uv sync 无法取得 Ershu 包 ​

常见表现： 安装报告某个 Ershu 组件版本不存在、uv.lock 缺失，或无法连接 Python 包源。

常见原因： 当前目录不是已发布标签，组件发布尚未完成，锁文件被改动，或网络代理无法访问包源。

处理：

  1. 确认部署目录来自已发布的标签或 Release 压缩包。
  2. 确认 uv.lock 存在且没有本地修改。
  3. 检查错误中的组件版本是否已经出现在配置的包源。
  4. 检查 UV 使用的代理、证书和包源地址。

恢复判据： uv sync --locked --extra all 正常结束，且没有重写锁文件。跳过某个组件不算完整组合安装成功。

前端依赖安装或启动失败 ​

先检查版本：

bash
node --version
npm ci
1
2

当前前端固定 Node.js 24。成功时，版本输出以 v24 开头，npm ci 以退出码 0 结束。不要用更新锁文件的方式掩盖版本不匹配。

若 npm run dev 已启动但页面空白，打开浏览器控制台并检查终端中的构建错误。修复后，http://localhost:3000 应进入设置、登录或项目页。

前端显示网络错误或一直停在加载状态 ​

先直接检查 API：

text
http://127.0.0.1:8000/health
1
  • 无法连接：API 没有启动、端口不同，或被本机网络规则阻止。
  • 返回状态 ok：API 进程存活，继续检查前端代理。

前端开发环境默认把 /api 转发到 http://localhost:8000。如果 API 在其他地址，修改 .env.local 的 VITE_DEV_API_PROXY 并重启 npm run dev。

恢复判据： 打开前端根地址后，页面能根据数据库状态进入首次管理员设置、登录或项目列表，不再持续显示请求失败。

/health 正常，但项目操作仍失败 ​

/health 和 /api/v1/health 只表示 API 进程存活。依赖检查使用：

text
http://127.0.0.1:8000/api/v1/health/dependencies
1

这个响应检查数据库和 Milvus，状态可能是 ok 或 degraded。它不检查 Redis，所以即使返回 ok，仍不能证明登录限流、队列相关连接或 Worker 都正常。

处理： 根据响应中的 database 和 milvus 结果检查地址、凭据和服务状态；Redis 与 Worker 需要单独检查。

运行长时间停在 queued ​

最可能的原因： Worker 没有运行，或 Worker 和 API 没有连接到同一套数据库。

处理顺序：

  1. 确认 uv run ershu-worker 进程仍在运行。
  2. 确认 API 和 Worker 使用同一份数据库、Redis、Milvus 与相关密钥配置。
  3. 查看 Worker 当前错误，重点检查仓库凭据、分支和模型通道。
  4. 修复根因后再决定取消或重试，不要连续创建相同运行。

恢复判据： 运行从 queued 进入 scanning、analyzing 或 finalizing，详情页开始出现新的时间线内容。

第一次运行不能选择单仓库或增量 ​

这是预期限制，不是前端故障。项目必须先建立覆盖全部活动仓库的完整项目基线。

选择 完整项目（full_project）并保留全部活动仓库。基线成功后，能力接口才可能开放单仓库或增量类型，具体以当前项目返回的选项为准。

恢复判据： 第一次完整项目运行可以提交，并出现在运行列表中。

运行因模型配置失败 ​

仓库分析必须有可用的 LLM 通道。模型名称、API Key 和地址不从 .env 读取。

进入管理员的模型通道页面，确认：

  • 至少一个 llm 通道已启用；
  • 连接或模型测试可用；
  • 项目或运行选择了有效通道；
  • 通过非本机地址提交密钥时使用 HTTPS。

恢复判据： 新运行不再因缺少 LLM 通道立即失败，并能进入扫描或分析阶段。

语义搜索不可用，或混合搜索显示降级 ​

先检查最近运行的 search_index_status：

  • indexed：语义索引已建立；
  • degraded：部分能力不可用，应阅读警告；
  • unavailable：当前没有可用语义索引。

语义搜索不可用时不会悄悄伪装为关键词结果。混合搜索可以明确回退到关键词，并在页面显示降级提示。

处理： 确认有独立、已启用的 embedding 通道，运行选择了它，并检查运行警告和 Milvus 依赖状态。

恢复判据： 新的完整分析建立索引后，语义查询能够返回结果，页面也不再显示未处理的降级原因。

Docs 没有文档，或问答没有上下文 ​

依次检查：

  1. 最近运行是否为 completed 或 completed_with_warnings。
  2. 运行详情是否真的列出生成文档。
  3. 带警告完成时，是否有仓库或文档生成阶段失败。
  4. 问答使用的项目是否正确。
  5. 项目是否有可用模型通道和可检索内容。

Docs 中的问答始终是项目范围，不会自动缩小到当前文档或章节。回答引用不同仓库并不一定是范围错误。

恢复判据： Docs 能打开生成文档；问答返回内容时，引用可以打开对应来源预览。

登录后写请求被 CSRF 或安全策略拒绝 ​

本地开发优先使用 localhost 或 127.0.0.1。生产或通过其他主机名访问时必须使用 HTTPS。

若 HTTPS 在反向代理终止，请检查：

  • 外部 Host 和 Origin 被原样传递；
  • X-Forwarded-Proto 是真实的外部协议；
  • API 信任实际代理来源；
  • Cookie 和允许来源配置与外部地址一致。

不要通过关闭 CSRF 或安全 Cookie 来让请求通过。

恢复判据： 登录可以恢复会话，创建项目、保存模型通道等 Cookie 鉴权写请求不再被判为跨站或非安全请求。

MCP 客户端连接到了错误端口 ​

同源部署中，/api/ 应转发到 API 的 8000 端口，/mcp/ 应转发到 MCP 的 8001 端口。不能把 /mcp/ 送到 API，也不能在代理时意外删除 MCP 路径前缀。

恢复判据： API 页面继续正常工作，MCP 客户端也能通过单独的 /mcp/ 地址建立连接。

已完成运行不再出现实时事件 ​

这是预期行为。活动运行使用快照和游标后的事件；completed 与 completed_with_warnings 直接读取最终结果，不再连接事件流。failed 和 cancelled 也不会继续接收实时事件。

恢复判据： 刷新已完成运行后，页面直接显示最终文本、分析块、警告和文档，而不是重新播放早期输出。

前端检查失败 ​

按失败命令分别处理：

bash
npm test
npm run lint
npm run format:check
npm run build
1
2
3
4
  • 测试失败：先修正状态逻辑或请求约定，不要删除断言。
  • lint 失败：同时检查代码规则和 TypeScript 错误。
  • 格式检查失败：只重新排版本次修改的文件，避免覆盖无关改动。
  • 构建失败：从第一个构建错误开始处理，不要只看最后一行。

四条命令都以退出码 0 结束，并且构建生成 dist/，才表示自动检查完成。浏览器中的中英文、主题、窄屏和长任务刷新仍需手工检查。完整的前端修改流程见开发前端。
