整体架构与关键数据流 ​

Ershu 由四个运行进程和一个共享包组成。Core 会安装进 API、Worker 和 MCP 的环境中，它本身不监听端口。

五个模块的边界 ​

Core：共同事实与规则 ​

Core 定义数据库模型、升级记录、项目权限、运行状态、仓库工作区、检索接口、模型通道与运行时设置契约。其他后端模块可以调用这些公共服务，但不能把自己的 HTTP 或后台任务逻辑反向放进 Core。

PostgreSQL 是业务事实来源：用户、项目、仓库、权限、运行队列、文档元数据和配置覆盖都在这里持久化。Milvus 保存语义检索所需的向量数据。Redis 只承担短期缓存、租约或协调职责，不能作为任务结果来源。

API：面向网页的控制面 ​

API 暴露 FastAPI 路由，负责 OPAQUE 登录、会话 Cookie、CSRF、项目和仓库管理、模型通道、运行创建与恢复、文档、搜索、关系查询和管理操作。

创建运行时，API 校验项目权限、分析类型、仓库范围和基线条件，再通过 Core 写入运行与队列记录。它不会在请求进程中分析代码。ershu-api-poller 是同仓库的独立进程，用租约协调定时仓库检查。

Worker：执行分析的数据面 ​

Worker 领取持久队列中的可用任务，为目标提交准备受限工作区，然后按阶段建立仓库树、代码索引、知识关系、搜索索引和项目文档。它持续写入阶段、检查点、事件、用量与最终结果，使 API 可以在连接中断后恢复读取。

只读仓库工具会限制路径、文件大小和调用预算，也不会执行仓库脚本。语言服务运行在受控环境中；当前支持的语言能力和依赖准备不是同一概念，例如 Java 语言服务存在，但不会自动执行 Maven 依赖准备。

MCP：面向开发智能体的只读面 ​

MCP 通过 Streamable HTTP 提供项目解析、文档、树、代码索引、关系、搜索和上下文查询工具。请求先验证 Bearer 凭据，再按密钥范围和项目权限调用 Core 服务。

MCP 工具不能创建项目、修改仓库或启动运行。需要改变状态的工作应走网页或 API。当前服务器注册 27 个工具；工具数量属于本版本事实，不应被客户端写成永久常量。

Frontend：人的工作区 ​

前端是 React 单页应用，通过 API 客户端调用 HTTP 与 SSE。它提供登录、项目切换、仓库和运行、文档阅读与问答、代码搜索、关系图、MCP 密钥以及系统管理页面。

页面刷新后，前端会先恢复登录状态，再从 API 读取持久运行快照；实时事件只是加快更新，不是唯一状态来源。前端不直接知道数据库或 Worker 实例。

任务以队列记录为恢复边界。Worker 通过租约避免同一任务被多个实例同时执行；实例失联后，符合恢复条件的任务可以重新进入可领取状态。调用方必须根据最终状态判断成功，不能把 HTTP 创建成功当成分析成功。

增量分析怎样保持项目视图？ ​

首次 full_project 运行会固定所有有效仓库的提交，建立项目基线。后续增量运行只处理发生变化的仓库和提交，但输出仍属于项目级视图。API 会拒绝缺少基线的增量请求。

Cron 轮询和 Webhook 都先解析仓库变化，再创建普通运行。Webhook 签名验证使用时间戳、空字节、随机数、空字节和原始请求体拼接的数据；任何代理或中间件都不应先重写请求体。

读取结果的三条路径 ​

路径适合的使用者特点
前端团队成员和管理员完整管理、可视化和交互式跟踪
API自动化与前端开发可以改变状态，也提供快照和查询接口
MCP开发智能体只读、项目范围、返回可继续核对的来源

修改架构时，优先保持这三条边界：状态改变留在 API，长任务留在 Worker，共享数据和规则留在 Core，智能体查询留在 MCP，人的交互留在前端。

事实来源：各模块入口、依赖清单、导入边界测试、运行队列模型、Worker 分析阶段、MCP 工具注册表和前端路由。
