扩展 MCP 与 Worker ​

MCP 与 Worker 都依赖 Core，但职责完全不同：MCP 把已经存在的只读查询安全地交给开发智能体；Worker 在后台读取仓库、提取事实、建立索引和生成文档。新增能力前先判断它属于“读取已有结果”还是“生产新结果”。

如果多个入口都需要同一查询，先把数据规则和权限规则放进 Core；MCP 只做参数边界、鉴权调用和适合上下文窗口的结果压缩。不要让 MCP 复制一套业务查询，也不要让 Worker 通过 MCP 反向读取自己的结果。

新增一个 MCP 工具 ​

1. 先定义共享读取能力 ​

工具若读取项目、仓库、文档、关系或契约，应优先复用 Core 的服务和响应类型。共享服务负责：

  • 项目和仓库归属校验；
  • 用户读取或管理权限；
  • MCP 密钥的项目范围；
  • 新鲜度、证据和数据可用状态；
  • 审计记录。

只有 MCP 会使用的轻量导航逻辑可以留在 mcp/src/ershu/mcp/，但仍要调用 Core 的权限和数据边界。

2. 在 server.py 增加异步包装 ​

工具函数应使用有范围的参数类型。项目参数使用 UUID、slug 或唯一可读名称；分页、深度、源码行数和查询长度都要给出明确上限。

项目工具通过 run_project_tool 执行，会先认证，再解析项目引用。服务级工具通过 run_session_tool 执行。需要直接控制会话时，也必须使用 authenticated_session，不能绕开 Authorization: Bearer ...。

返回内容较大时，在 payload_compaction.py 增加专用压缩函数，只移除重复或低价值字段。提交、来源、authority、新鲜度、覆盖范围、截断和降级信息不能为了缩短结果而丢失。

3. 显式注册工具 ​

把新函数加入 server.py 的 _registered_tools()。只有定义函数而未注册，客户端不会看到它。get_server_info 的 capabilities 也直接来自这份注册表，因此注册后的可观察结果是工具名出现在该调用中。

4. 补齐安全测试 ​

至少验证：

  • 没有 Bearer 凭据时拒绝调用；
  • 密钥超出项目范围时不泄露项目是否存在；
  • 用户没有读取或管理权限时拒绝；
  • 仓库编号不能跨项目使用；
  • 分页和输入上限在边界值之外会失败；
  • 审计记录不含查询密钥或仓库凭据；
  • 压缩结果仍保留提交、证据和状态字段；
  • _registered_tools() 与 get_server_info 都出现新名称。

新增 Worker 事实提取器 ​

1. 实现统一协议 ​

通用仓库事实提取器实现 GraphFactExtractor，位置在 worker/src/ershu/workers/services/fact_extractors/。它接收受限扫描上下文，产出节点、边、证据、未知项和度量，不应自行执行仓库脚本。

事实需要稳定标识，并保留来源文件、行号或其他可回到源码的锚点。无法确定时记录未知项，不要把猜测写成确定关系。

2. 注册提取器并声明规则 ​

在提取器注册表中加入实现，并在 Core 的知识关系规则包中声明对应规则。注册表会检查规则覆盖：存在提取器却没有规则，或规则没有实现，都会让注册校验失败。

改动规则含义时要递增规则包版本，使已有事实可以被识别和重建。不要直接复用一个旧规则编号表达不同语义。

3. 对框架路由使用专门注册表 ​

新增 Web 框架静态路由识别时，实现一个 FrameworkRouteExtractorSpec，声明框架名、规则编号、文件后缀、检测条件和扫描函数，再加入框架路由注册表。公共组装逻辑负责把路由、操作、处理器和证据转为统一事实。

测试既要覆盖确定命中，也要覆盖动态路径、无法解析的声明和“像路由但不支持”的信号，避免静默漏报。

新增 Worker 分析 Agent 工具 ​

Agent 工具有一份统一注册表。新增工具必须同时提供：

  1. 输入 schema；
  2. 可执行 handler；
  3. 结果摘要函数；
  4. 面向模型的清楚描述。

注册校验要求展示名单与执行名单一致。只增加 schema 会得到“没有 handler”，只增加 handler 会得到“没有 schema”。工具仍应保持只读、限定路径和限定返回量，并在结果中明确未知项与截断。

扩展 LSP 语言支持 ​

这不是只改一个镜像名称的工作。当前适配组包括 Python、TypeScript/TSX/JavaScript、Go、Rust、C/C++ 和 Java。新增语言至少会跨越：

  • Core 的语言与源码后缀注册表；
  • Worker 的 LSP 适配组、默认镜像和允许值；
  • Docker 只读、断网、资源限制和清理流程；
  • 能力探测、依赖准备与错误状态；
  • 配置范围、镜像测试、协议测试和端到端索引测试。

依赖准备与 LSP 是两个沙箱。可选的准备沙箱只下载受支持的锁定依赖；LSP 容器仍然断网、只读。当前受管理的锁文件生态是 Go、npm、Python 和 Cargo；Java Maven 与 Gradle 尚未进入这条准备流程。

不要只看测试退出码。MCP 扩展还应在实际客户端的 get_server_info 中出现，并通过受限密钥完成一次允许和一次拒绝调用。Worker 扩展还应在测试仓库上生成带源码锚点的预期事实，对不支持或不确定输入返回明确状态，并且不修改工作区。

提交前分别检查 MCP 和 Worker 仓库的变更，确认没有把共享规则复制到两个模块，也没有把测试专用分支带进生产路径。
